# RFC 0027.b: Cluster-native `dataflow!` — merged design

Status: **merged design / implementation-ready PRD**. This document replaces the draft capture in [RFC 0027.a](./0027.a-cluster-native-dataflow.md) with a single, self-contained product requirements document. It selects the best-practical alternatives from the multi-agent critique, resolves cross-theme tensions, pins operational parameters, and maps acceptance criteria to the project’s stated rubric.

---

## 1. Vision

Nirdosha stream-compute topologies are today confined to a single OS process: the `dataflow!` surface, deterministic-operator contract, seeded RNG, bounded local channels, and per-node `DurableLog` already give the *language* a cluster-compatible shape, but there is no inter-node substrate to make one process and many processes the same deployment artifact. This RFC closes that gap.

The goal is a cluster-native `dataflow!` runtime extension where:

- The **same compiled binary** runs on one process or on a fleet of identical processes, distinguished only by runtime configuration and attestation.
- Adding or removing a node changes **only source-partition ownership** inside a single consumer group; no JobManager/TaskManager-style special roles are introduced.
- A failed node’s partitions resume elsewhere by **restoring the latest snapshot and replaying from the committed offset**, reconstructing byte-identical state because operators are deterministic and RNG is offset-seeded.
- HTTP/webhook ingress, repartitioning, state snapshots, barriers, watermarks, and exactly-once sinks are all mediated through a **shared durable log**; there is no direct socket mesh or RPC between operators or between nodes.
- Every `V2_GUARANTEES.md` guarantee — `deterministic_execution`, `durable_transactions`, `authenticated_identity`, `build_provenance`, `deadlock_freedom` — is evidenced at **fleet scale**, not just per-node.

This is **not** a new language syntax project. The `dataflow!` macro, `#[contract(..)]`, and driver passes remain unchanged. Clustering is expressed through runtime configuration, provider URLs, and the certificate/guarantee bundle.

> **Rubric anchoring:** This section satisfies *Practical* (reuses the existing v1 surface and identical-process model), *Grounded* (inherits RFC 0027, RFC 0027.a, and `V2_GUARANTEES.md`), and *Innovative* (cluster scale without special roles).

---

## 2. Goals

1. **Identical-process deployment.** Every process runs the same compiled topology; a single process is a one-member cluster.
2. **Partition-ownership work distribution.** Source partitions are the unit of work; consumer-group membership decides which process owns which partition.
3. **Log-backed cross-node shuffle.** Repartitioning and cross-node traffic happen only through the shared durable log.
4. **Deterministic replay after failure.** Rebalance/failover restores partition state from snapshots and replay; operators are pure and RNG is offset-seeded, so state is byte-identical across nodes.
5. **Exactly-once sinks at fleet scale.** Offset commit dominates the sink effect; provider transactions or idempotent sink keys make the external effect appear once.
6. **Fleet-scale v2 guarantees.** Static fleet guarantee bundles plus runtime audit hooks provide evidence for all five cluster-scaled guarantees.
7. **Single-node compatibility.** `EmbeddedLog` mode keeps today’s single-node tests running unchanged.

## 3. Non-goals

1. **Multi-input joins and session windows** are **out of the first milestone** (Phase 0–3). The design must not foreclose them, but driver/runtime proof of global watermark alignment for joins is deferred to Phase 4.
2. **Self-contained consensus** (Raft + SWIM) is a future Phase 5 track; Phase 0–3 target an external Kafka-compatible log.
3. **Native iOS/Android generation** from dataflow topologies is out of scope.
4. **Changing `dataflow!` syntax** for clustering — the surface stays the same.
5. **Guaranteeing exactly-once to arbitrary non-idempotent external APIs** — the runtime can only guarantee this when the sink target is in the supported-provider set or the operator supplies its own idempotency key.

## 4. The chosen innovations

Each subsection specifies the mechanism, data/control flow, interfaces, and key behaviors. Residual ambiguity is marked `OPEN QUESTION:` explicitly.

### 4.1 `LogProvider` abstraction and identical-process execution model

#### Mechanism

The v1 embedded `DurableLog` is generalized behind a `LogProvider` trait. Two initial implementations are required:

| Implementation | Mode | Backing store |
|---|---|---|
| `EmbeddedLog` | single-node | Local files + SQLite/offset store |
| `KafkaLog` | cluster | External Kafka/Redpanda topic |

Selection is runtime configuration, never source syntax. The `dataflow!` source declaration stays:

```rust
source ledgerlog: DurableLog<LedgerTxn> = "ledger";
```

The runtime maps the logical source name `ledger` to the configured provider topic using the configured provider URL.

Every process runs the **full compiled topology**, but only over the source partitions it currently owns. Each owned partition gets its own local executor containing the same operator graph. Local edges remain bounded channels exactly as in v1.

#### `LogProvider` trait (minimal contract)

```rust
pub trait LogProvider: Send + Sync {
    fn list_partitions(&self, topic: &str) -> Result<Vec<PartitionId>, Error>;
    fn assign_partitions(&self, partitions: &[PartitionId]) -> Result<(), Error>;
    fn revoke_partitions(&self, partitions: &[PartitionId]) -> Result<(), Error>;
    fn poll_partition(&self, partition: PartitionId, max_records: usize)
        -> Result<Vec<Record>, Error>;
    fn append(&self, topic: &str, key: &[u8], value: &[u8])
        -> Result<Offset, Error>;
    fn commit_offset(&self, partition: PartitionId, offset: Offset) -> Result<(), Error>;
    fn open_transaction(&self, txn_id: &str) -> Result<Box<dyn LogTxn>, Error>;
    fn snapshot_topic(&self, source_topic: &str) -> String; // e.g. "__nirdosha_snapshots_<source_topic>"
    fn control_topic(&self) -> String; // "__nirdosha_control"
}

pub trait LogTxn: Send + Sync {
    fn send(&mut self, topic: &str, key: &[u8], value: &[u8]) -> Result<(), Error>;
    fn send_offsets_to_transaction(&mut self, partitions: &[(PartitionId, Offset)]) -> Result<(), Error>;
    fn commit(self: Box<Self>) -> Result<(), Error>;
    fn abort(self: Box<Self>) -> Result<(), Error>;
}
```

For `EmbeddedLog`, `open_transaction` is implemented with a SQLite transaction across the local offset store and snapshot topic.

For `KafkaLog`, `open_transaction` is implemented with a Kafka producer transaction using the provider’s `transactional.id` fencing.

#### Key behaviors

- A process starts, joins the consumer group identified by `group_id`, and receives partition assignments through the provider’s group protocol (KIP-848 incremental cooperative rebalance for Kafka/Redpanda).
- On assignment: load the latest snapshot for the partition, replay from the snapshot offset to the committed offset, then resume live polling.
- On revocation: stop polling the revoked partition, drain in-flight records to the next barrier, snapshot state, commit the final offset, then release the partition.
- Cross-node traffic is produced as keyed records to a repartition topic; the downstream operator reads only the repartition partitions assigned to its node.
- There is **no direct node-to-node socket mesh**, no gRPC/HTTP between operators, and no per-operator process.

> **Rubric anchoring:** Satisfies *Practical* (reuses v1 `DurableLog` shape), *Performant* (poll-based, asynchronous data path), and *Grounded* (RFC 0027.a §3/§4, RFC 0011 provider model, `crates/nirdosha-ingestion-topic-kafka`).

### 4.2 Membership, partition ownership, and node identity

#### Mechanism

Membership uses the provider-native consumer group in external mode. The self-contained mode (Phase 5) will layer SWIM + Raft behind the same `LogProvider` trait; the surface is unchanged.

Node identity and attestation follow Row 12 (`VerifiedIdentity`, `RoleView`) and the existing guarantee-bundle machinery:

1. Every binary is produced by `cargo nirdosha verify`, which emits:
   - the compiled binary,
   - a certificate `contract-report-<package>.json`,
   - a guarantee bundle `target/nirdosha/guarantees-<package>.json` (verified by `crates/cargo-nirdosha/tests/guarantee_bundle.rs`).
2. The guarantee bundle gains cluster fields: `provider`, `group_id`, `partition_count`, `exactly_once_mode`, `snapshot_backend`, `topology_hash`.
3. At startup and at every group join, the runtime:
   - verifies the certificate signature against the configured trust anchor,
   - checks that the bundle’s `group_id` and `cluster_id` match the runtime configuration,
   - checks that the bundle’s `topology_hash` matches the running binary’s hash,
   - rejects membership if any check fails.
4. Broker-level enforcement is required for real security: the provider must be configured with mTLS or token-based ACLs that only allow binaries presenting the fleet’s certificate/identity to join the consumer group. The runtime self-check is necessary but not sufficient against a compromised binary that simply skips the check.

#### Interface

```rust
pub struct FleetConfig {
    pub cluster_id: String,
    pub group_id: String,
    pub provider_url: String,          // e.g. "kafka://broker:9092"
    pub trust_anchor_path: PathBuf,    // fleet signing public key / CA
    pub bundle_path: PathBuf,
    pub mtls_identity: IdentityConfig,   // broker ACL identity
}

pub trait FleetAttestation {
    fn audit_bundle(&self, binary_path: &Path, bundle: &Value) -> Result<(), AttestationError>;
    fn join_group(&self, provider: &dyn LogProvider) -> Result<(), AttestationError>;
}
```

#### Key behaviors

- A node that fails attestation **exits before joining the provider group**.
- A node whose bundle is valid at startup but whose runtime later loads an unapproved native library or calls wall-clock inside an operator is detected by periodic deterministic-runtime self-checks (see §4.6) and by the driver’s static rejection of `Instant`/`std::time` in deterministic operators.
- The provider group is the source of truth for partition ownership; attestation is a gate before the runtime is allowed to participate in that group.

> **Rubric anchoring:** Satisfies *Practical* (builds on `cargo nirdosha verify` and `check-certificate` already implemented), *Performant* (audit is off-path), and *Grounded* (`crates/cargo-nirdosha/tests/guarantee_bundle.rs`, `docs/V2_GUARANTEES.md`, RFC 0017 §4, RFC 0027.a §11).

### 4.3 Time, barriers, and watermarks — bounded wall-clock liveness envelope

#### Mechanism

The deterministic core remains wall-clock-free. Watermarks are computed from source offsets and the declared `event_time` field. A **barrier** is a control record injected into the source log and the repartition topics. Completion of barrier `e` for a partition means all data records before `e` in that partition have been processed.

To close the **idle-source liveness hole** (a partition with no records would never advance its watermark), a **liveness watch** observes wall-clock *outside* the data path. When a partition has not produced a new record or barrier within `max_barrier_idle_ms`, the watch appends a `BarrierTimeout` control record to the shared `__nirdosha_control` topic. Every process consumes `__nirdosha_control` in total order. The timeout record makes the epoch complete deterministically for all consumers.

A **barrier epoch** is a logical counter that advances only when:
- a source partition has processed `max_records_per_barrier` records, **or**
- a `BarrierTimeout` record is committed for that epoch, **or**
- a membership change forces a drain-to-barrier.

Wall-clock is **never an input to operator logic or watermark arithmetic**. It is used only by the liveness watch to produce durable control records; once written, those records become part of the deterministic log and drive identical decisions everywhere.

#### Control-log records

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
pub enum ControlRecord {
    /// Epoch advance forced by idle timeout.
    BarrierTimeout {
        epoch: u64,
        source_topic: String,
        partition: PartitionId,
        /// Deterministic set of partitions that had not completed by the timeout.
        /// Computed by a canonical rule over observed state; see tie-breaking below.
        timed_out_partitions: BTreeSet<PartitionId>,
    },
    /// Snapshot metadata written atomically with the provider transaction.
    SnapshotMeta {
        epoch: u64,
        source_topic: String,
        partition: PartitionId,
        offset: Offset,
        snapshot_key: String,       // content-addressed key or compacted changelog key
        state_hash: [u8; 32],       // Merkle root of canonical state
    },
    /// Intent for exactly-once sink effect.
    SinkIntent {
        epoch: u64,
        partition: PartitionId,
        intent_id: String,
        sink_name: String,
    },
}
```

#### Tie-breaking for concurrent timeout records

Multiple processes may independently write `BarrierTimeout` for the same epoch. The payload must be keyed with a deterministic idempotency key so the provider deduplicates identical writes. The `timed_out_partitions` set is computed by the rule:

```
timed_out_partitions = { p | p is in the same source topic and p has not emitted
                       a BarrierComplete record for this epoch }
```
where `BarrierComplete` is an internal per-process record, not a control-log write. Because every process consumes the same source partitions and control topic in the same order (modulo per-partition data), the rule is deterministic enough for liveness; if payloads differ, the first record in `__nirdosha_control` order wins and later duplicates are ignored.

#### Watermark computation

- **Per-partition watermark:** `min(event_time of all unclosed records in partition p up to current epoch)`.
- **Combined watermark (for future multi-input operators):** `min(per-partition watermark over all input partitions)`. Phase 0–3 do not need combined watermarks for single-input topologies, but the control topic and epoch model are designed to support them.

#### Key behaviors

- Operators never read `__nirdosha_control`, wall-clock, or liveness metadata. The driver enforces this by treating access to those types as impure/non-deterministic.
- `event_time` derives only from the declared field in the data record and the source offset.
- Barrier completion triggers state snapshots, watermark advancement, and sink intent alignment.

> **Rubric anchoring:** Satisfies *Zero-ambiguity* (defines idle fallback, tie-breaking, and deterministic core separation), *Practical* (grounded in `transact/durable.rs` and `workflow/outbox.rs` lease semantics), and *Innovative* (wall-clock as liveness oracle, not data input).

### 4.4 State snapshots, restore, and deterministic replay

#### Mechanism

State is scoped **per partition**, not per process. Within a process, each owned partition gets its own `StateHandle<K,V>` namespace keyed by `(topic, partition, epoch)`.

On barrier completion, the runtime:

1. **Serializes the partition state to a canonical byte representation** (see §4.4.1).
2. Writes the serialized state to the provider snapshot topic (compacted changelog) or, in self-contained mode, to a shared object store.
3. Writes a `SnapshotMeta` control record linking `(epoch, offset)` to the snapshot.
4. Commits the source offset inside the same provider transaction that writes the snapshot record.

Restore is:

1. Read the latest `SnapshotMeta` whose `offset ≤ committed_offset`.
2. Load the referenced snapshot bytes.
3. Replay records from `snapshot.offset` to `committed_offset` through the deterministic operators.
4. Resume live polling from `committed_offset`.

Because operators are deterministic and RNG is offset-seeded, replay reconstructs byte-identical state. A Merkle root (`state_hash`) in `SnapshotMeta` lets the new owner verify that the loaded state matches the attested snapshot.

#### 4.4.1 Canonical deterministic serialization

The runtime must serialize the following into a **byte-identical** representation across processes and restarts:

- All `StateHandle<K,V>` entries for the partition.
- All pending sink intents and uncommitted outbox rows for the partition.
- Any window/session state held by the runtime for the partition.

The canonical format is defined as:

1. **Sort all entries** by a stable ordering of keys.
2. **Serialize keys and values** using a schema-driven binary codec with:
   - fixed-width integers (little-endian `i64`, `u64`, `i32`, `u32`),
   - length-prefixed byte arrays for strings and blobs,
   - sorted map iteration order,
   - no floating-point values in keys,
   - NaN handling for float values (if any) normalized to a single canonical NaN bit pattern,
   - enum variants as discriminant-index-then-payload,
   - no timestamps or wall-clock fields from the host.
3. **Compute a Merkle tree** over the sorted entries; the root is the `state_hash` stored in `SnapshotMeta`.
4. The snapshot record itself is `(state_hash, epoch, partition, bytes)`.

For user-defined `V` types, the compiler emits a deterministic serializer alongside the regular `Serialize` impl. This emitted serializer is what the runtime uses for snapshots. The driver checks that the type does not contain wall-clock, raw pointers, or other non-deterministic fields.

#### Compaction safety rule

Compacted changelog topics must **never discard every snapshot older than a live committed offset**. Concretely:

- Retain the latest snapshot for each partition.
- Retain every snapshot whose `offset` is greater than the minimum committed offset across all live consumers in the group.
- GC removes only snapshots whose `offset` is less than the minimum live committed offset minus a safety margin (`snapshot_gc_margin = 24 hours of offsets`).

For `EmbeddedLog` single-node mode, compaction is local file rotation with the same rule.

#### Key behaviors

- Full snapshots are taken every barrier. **Incremental/delta snapshots are Phase 4 optimization**, not required for the first milestone. To bound hot-path overhead, snapshots are written asynchronously after the barrier completes; the `SnapshotMeta` record is committed atomically with the offset, but the bytes may land slightly later using the content-addressed key.
- Large snapshots are chunked into `max_snapshot_chunk_size = 1 MiB` records. The `SnapshotMeta` references the ordered list of chunk keys.

> **Rubric anchoring:** Satisfies *Practical* (reuses provider topic model), *Zero-ambiguity* (canonical serialization and compaction safety rule specified), and *Grounded* (`crates/nirdosha-workflow/src/outbox.rs`, `crates/runtime-kernels/src/kernel/transact/durable.rs`, RFC 0027.a §5.2).

### 4.5 HTTP ingress, sinks, and exactly-once side effects

#### Mechanism

HTTP/webhook ingress follows the outbox/relay shape already used by `DurableSaga` and `wf_outbox`:

1. Every process exposes the `HttpWebhook<T>` route.
2. A load balancer distributes POSTs across the fleet.
3. The receiving process appends the event to the shared source topic using an idempotent producer keyed by a caller-supplied idempotency header or a deterministic request fingerprint.
4. The process returns **HTTP 202 Accepted** only after the log provider acknowledges durable replication to its configured in-sync replicas.
5. Downstream processing is asynchronous from the log.

#### Source-level `event_id` requirement

Every `HttpWebhook<T>` source requires `T` to declare an `event_id: str` field. This is a new compile-time check performed by the `dataflow!` macro expansion and the driver. The `event_id` is used as the log append idempotency key when the caller does not supply one.

- For new topologies: the source type must contain `event_id: str` directly.
- For v1 webhook sources without `event_id`: the runtime synthesizes an `event_id` from a canonical hash of `(request method, path, stable headers, body)` and rewrites the type during macro expansion. This is a compatibility shim, not the preferred path.

#### Exactly-once sinks

The driver statically verifies one of the following for every `exactly_once` sink:

1. The sink target is listed in `provider_capabilities.json` as supporting idempotency under the declared `intent_id` key (e.g. a REST API with an `Idempotency-Key` header, a database upsert on `intent_id`, or a Kafka topic with the same key).
2. The operator supplies its own idempotency mechanism and the driver can prove it is invoked on every path before the effect.

The runtime commit order for an `exactly_once` sink within barrier `e` is:

```
1. append SinkIntent { epoch, partition, intent_id } to __nirdosha_control
2. offset_commit(partition, offset) inside the provider transaction
3. perform the external effect keyed by intent_id
4. commit the provider transaction (for Kafka-native sinks, this also commits produced records)
```

If the process crashes between steps 2 and 3, replay from the committed offset re-drives the sink. The `intent_id` deduplicates the second attempt.

If the process crashes before step 2, the effect is not visible externally and replay resumes before the sink call.

`at_least_once` sinks skip the transaction and the intent record; duplicates are possible and must be tolerated or deduplicated by the operator.

#### Bounded operational parameters

| Parameter | Default | Bounds | Rationale |
|---|---|---|---|
| `max_records_per_barrier` | 10,000 | [100, 1,000,000] | Barrier frequency vs. snapshot overhead |
| `max_barrier_idle_ms` | 5,000 ms | [100 ms, 60,000 ms] | Idle-source liveness |
| `global_complete_timeout` | 60,000 ms | [1,000 ms, 300,000 ms] | How long to wait for all partitions to complete a barrier |
| `lease_duration` | 30 s | [1 s, 300 s] | Sink intent/in-flight lease, consistent with `wf_outbox` |
| `max_in_flight_repartition` | 1,000 records/partition | [10, 100,000] | Cross-node backpressure credit |
| `repartition_partition_count` | 16, power of two | [1, 1,024] | Downstream parallelism for repartition topics |
| `max_snapshot_chunk_size` | 1 MiB | [64 KiB, 16 MiB] | Broker message-size limit |
| `snapshot_gc_margin` | 24 hours of offsets | [1 hour, 7 days] | Compaction safety margin |
| `provider_log_retention` | 7 days | [1 day, 90 days] | Minimum log retention |

> **Rubric anchoring:** Satisfies *Practical* (reuses `DurableSaga`/`wf_outbox` lease model), *Performant* (bounded in-flight caps, build-time idempotency checks), *Zero-ambiguity* (commit order and failure windows pinned), and *Grounded* (`crates/nirdosha-workflow/src/outbox.rs`, `crates/runtime-kernels/src/kernel/transact/durable.rs`, `docs/V2_GUARANTEES.md` `durable_transactions`).

### 4.6 Fleet-scale evidence for v2 guarantees

#### Mechanism

The primary evidence is a **static fleet guarantee bundle** produced at build time by `cargo nirdosha verify` and audited at node startup/join. The bundle is a signed JSON sidecar (`guarantees-<package>.json`) with the same provenance link to the certificate as today’s implementation (`crates/cargo-nirdosha/tests/guarantee_bundle.rs`).

Cluster-specific bundle fields:

```json
{
  "bundle_version": "1",
  "package": "rt-payroll",
  "source_hash": "<certificate hex binding>",
  "certificate": "contract-report-rt-payroll.json",
  "cluster": {
    "provider": "kafka",
    "group_id": "payroll-group",
    "cluster_id": "payroll-prod",
    "partition_count": 16,
    "exactly_once_mode": "provider_transaction",
    "snapshot_backend": "compacted_changelog",
    "topology_hash": "<hash of compiled topology + runtime config>",
    "rng_policy": "offset_seeded_per_record",
    "wall_clock_boundary": "liveness_oracle_only"
  }
}
```

At startup/join:

1. Verify the bundle signature against `trust_anchor_path`.
2. Recompute the binary/content hash and compare to `topology_hash`.
3. Compare `provider`, `group_id`, `cluster_id`, `partition_count`, `exactly_once_mode`, and `snapshot_backend` against runtime configuration.
4. If any mismatch, the node exits with `AttestationError::BundleMismatch` before joining the provider group.

#### Runtime enforcement layer

Static evidence is necessary but not sufficient. The runtime adds:

- A deterministic-runtime self-check task that periodically samples whether the process has loaded symbols or made syscalls outside the trusted runtime boundary (e.g. `clock_gettime` from operator code). This is a **best-effort detection** mechanism; it does not raise the guarantee to a formal proof.
- A signed heartbeat emitted to the control topic every `heartbeat_interval = 60 s` containing the node’s bundle hash and a monotonic epoch counter. This gives operators an audit trail of which binaries were alive when.
- The driver already rejects `Instant::now`, `std::time`, OS entropy, and unseeded RNG in operators claimed `deterministic`; this rejection is the actual enforcement wall.

> **Rubric anchoring:** Satisfies *Practical* (builds on shipped `cargo nirdosha verify` and `check-certificate`), *Performant* (off-path audit), *Grounded* (`crates/cargo-nirdosha/tests/guarantee_bundle.rs`, `docs/V2_GUARANTEES.md`, RFC 0017 §4, RFC 0027.a §11), and partially *Innovative* (fleet-wide attestation from build-time evidence).

## 5. Cross-theme integration

This section resolves the tensions between the recommended alternatives.

### 5.1 Wall-clock vs. deterministic execution

**Tension:** The essence states watermarks and execution never use wall-clock, but the selected barrier design uses a wall-clock liveness watch.

**Resolution:** Wall-clock is confined to a **liveness oracle** that emits durable control records. Operators and watermark arithmetic consume only log records (data and control). The deterministic core is preserved because:

- The liveness watch is a runtime task, not an operator.
- `BarrierTimeout` records are appended to the shared log and consumed identically by all processes.
- The driver rejects any operator that reads wall-clock, `__nirdosha_control` metadata, or liveness state.
- Watermarks continue to derive from source offsets and declared `event_time`; a `BarrierTimeout` does not inject synthetic `event_time`, it only closes the current epoch so that the existing watermark can advance in the absence of data.

**Invariant reframed:**
> *Operator execution and watermark values never depend on wall-clock. Wall-clock may only trigger durable log records that all processes observe identically.*

### 5.2 Full snapshots vs. bounded hot-path overhead

**Tension:** The selected snapshot strategy writes full state every barrier, which is potentially expensive.

**Resolution:**

- Snapshots are written **asynchronously** after barrier completion; only the small `SnapshotMeta` record is committed atomically with the offset.
- Large snapshots are chunked into 1 MiB records.
- The format is a compact binary canonical serialization, not JSON.
- `max_records_per_barrier` default (10,000) bounds snapshot frequency.
- Incremental/delta snapshots are explicitly deferred to Phase 4 as an optimization; full snapshots are correct and sufficient for Phase 0–3.

### 5.3 Compile-time idempotency vs. provider transaction

**Tension:** Side-effects theme C is compile-time verification; it does not supply the actual distributed commit primitive. Theme A supplies the primitive but is provider-specific.

**Resolution:** Use **both**, layered:

- **Compile time:** the driver/certificate rejects `exactly_once` sinks whose target is not in the supported-provider capability manifest or whose operator does not supply a proven idempotency mechanism.
- **Runtime:** the `LogProvider` transaction primitive (Kafka transaction or `EmbeddedLog` SQLite transaction) commits offset + `SinkIntent` atomically.
- The static bundle declares `exactly_once_mode: provider_transaction` so the runtime knows which path to use.

This keeps the verification in the existing driver/certificate pipeline while using the provider’s battle-tested transaction protocol for the actual distributed commit.

### 5.4 Static bundle vs. runtime attestation

**Tension:** A static bundle can be bypassed by a compromised process that simply skips the check.

**Resolution:**

- The bundle check is **mandatory** at startup and on every join; the runtime exits on failure.
- Broker-level mTLS/ACLs enforce that only fleet-identified clients can join the consumer group and produce to the source/repartition topics.
- A periodic runtime self-check and signed heartbeat provide detection, not proof, of mid-run tampering.
- A future Phase 5 control-log attestation mesh can be layered on without changing the bundle format or the startup gate.

### 5.5 Provider-native group vs. self-contained consensus

**Tension:** The first milestone relies on Kafka/Redpanda consumer groups, but the long-term vision is a self-contained Raft + SWIM mode.

**Resolution:** The `LogProvider` trait is the isolation boundary. `KafkaLog` is the Phase 0–3 implementation. `RaftLog` is Phase 5. Both implement the same trait, so the topology source code, driver checks, and certificate bundle format do not change.

## 6. Acceptance criteria mapped to the rubric

| Criterion | Acceptance criterion | How this PRD satisfies it |
|---|---|---|
| **Practical** | A single compiled binary runs unchanged on one process and on a fleet. | `EmbeddedLog` and `KafkaLog` share the same `LogProvider` trait and `dataflow!` surface; single-node tests use `EmbeddedLog`. |
| **Practical** | No new consensus implementation is required for the first milestone. | Phase 0–3 use external Kafka/Redpanda consumer groups and transactions. |
| **Performant** | Hot data path has no synchronous cross-node coordination. | Poll-based consume, log-append produce, credit-based in-flight cap; barriers and timeouts are log-backed, not RPC-backed. |
| **Performant** | Snapshot overhead is bounded. | Async snapshot writes, 1 MiB chunking, binary canonical format, full-snapshot default with Phase 4 delta optimization. |
| **Zero-ambiguity** | Every failure window is pinned. | §4.5 and §7 define behavior for pre-202, post-202, processing-node-death, and sink-mid-effect cases. |

## 7. Operational scenarios

This section pins the four failure windows from RFC 0027.a §7.

### 7.1 Node dies before returning HTTP 202

- Caller sees timeout or connection error and retries.
- Log append is idempotent by `event_id` or caller idempotency header.
- Result: at-least-once at network level; the log has exactly one record.

### 7.2 Node returns 202 but dies before provider fully replicates

- The 202 is returned only after the provider acknowledges replication to `min.insync.replicas`.
- Surviving the ingress node’s death is the provider’s durability contract.
- Nirdosha does not add a second guarantee on top.

### 7.3 Event is in the log, but the processing node dies

- Consumer group detects the failed member via provider session timeout.
- Partitions are reassigned to surviving nodes.
- New owner loads latest snapshot ≤ committed offset, replays to committed offset, resumes live processing.
- Because operators are deterministic and RNG is offset-seeded, state is reconstructed identically.

### 7.4 Sink effect is in flight when the node dies

- For `exactly_once` sinks: `SinkIntent` and offset are committed in the provider transaction before the effect. If the node dies between commit and effect, replay re-drives the sink and `intent_id` deduplicates.
- For `at_least_once` sinks: duplicates are possible; downstream must tolerate them.

## 8. Implementation phases

These phases follow RFC 0027.a §12 but tighten the scope and ordering.

### Phase 0 — `LogProvider` abstraction

- Define `LogProvider` and `LogTxn` traits.
- Implement `EmbeddedLog` first; all existing v1 tests run unchanged.
- Add runtime configuration: `provider_url`, `group_id`, `cluster_id`, `cluster_seed_nodes`.
- Add cluster fields to guarantee bundle.

### Phase 1 — Consumer group, per-partition executor, HTTP ingress

- Implement `KafkaLog`.
- Run one local topology executor per assigned partition.
- Implement assign/revoke lifecycle: drain-to-barrier, snapshot, commit offset, restore on rebalance.
- Wire `HttpWebhook<T>` to append to shared log and return HTTP 202 after durable replication.
- Add `event_id` compile-time check and v1 compatibility shim.
- Add `nirdosha-rt dataflow cluster status` CLI.

### Phase 2 — Repartition topics and cross-node shuffle

- Emit keyed repartition records when upstream/downstream `keyed(by = ...)` differ.
- Read assigned repartition partitions into local executor.
- Enforce `max_in_flight_repartition` credit cap.

### Phase 3 — Partitioned state snapshots + restore

- Snapshot keyed state per partition on barrier.
- Write snapshots to compacted changelog topic.
- Restore from snapshot + replay on rebalance.
- Implement canonical deterministic serializer and Merkle `state_hash`.

### Phase 4 — Global barriers and multi-input windows

- Coordinate barrier injection across all source partitions using `__nirdosha_control`.
- Implement combined watermarks.
- Add driver/runtime checks for compatible watermarks on multi-input operators.
- Add delta/incremental snapshot optimization.

### Phase 5 — Self-contained Raft + SWIM mode

- Implement SWIM membership.
- Implement Raft metadata log.
- Provide `RaftLog` `LogProvider` implementation.
- Add node identity and guarantee-bundle fleet attestation.

## 9. Open questions

1. **Canonical serializer implementation detail:** Should the deterministic serializer be a separate proc-macro-derived trait (`CanonicalSerialize`) or generated directly by the compiler backend? This affects crate boundaries and testability. Decision needed before Phase 3.
2. **mTLS/ACL operational model:** The PRD requires broker-level enforcement, but the exact trust-anchor format, certificate rotation policy, and provider ACL mapping are not specified. A follow-on security operations doc is needed.
3. **Control topic scaling:** `__nirdosha_control` is a single-partition topic. While control records are small, very large fleets may need a hashed multi-partition control topic. The PRD keeps it single-partition for Phase 0–3; scaling is deferred.
4. **Self-contained mode transaction semantics:** When `RaftLog` replaces `KafkaLog`, the exact mapping of `LogTxn` to Raft log entries (per-partition Raft group vs. shared log) is deferred to Phase 5.
5. **HTTP ingress idempotency header convention:** The exact header name, fallback fingerprint algorithm, and v1 compatibility shim expansion rules need to be specified in the macro implementation doc.
6. **Multi-input joins:** Global watermark alignment proof and repartitioning on a common join key are intentionally out of scope for Phase 0–3; the control-topic/epoch model is designed to support them.
7. **Runtime deterministic self-check precision:** The periodic self-check for wall-clock/native-library use is described as best-effort. Whether it can be made precise enough to detect a compromised operator binary is an open research/security question.
8. **Provider capability manifest format:** The exact schema and attestation binding for `provider_capabilities.json` are not specified in this PRD and require a companion ADR.

## 10. Relationship to other RFCs

- **RFC 0027** — this document amends it; v1 single-node design is retained as `EmbeddedLog`.
- **RFC 0027.a** — superseded by this merged design for implementation purposes.
- **RFC 0011** — `LogProvider` is a provider behind a port; the same two-driver rule and credential-stripped identity apply.
- **RFC 0006** — per-partition executors use the same structured concurrency primitives.
- **RFC 0007** — APM `Domain` ceilings apply per process, per partition.
- **RFC 0017** — the guarantee manifest gains cluster fields; fleet attestation is a new kind of evidence.

---

*This merged PRD keeps the v1 language and verification intact and adds only a distributed backplane. A single-process `dataflow!` program and a twenty-process cluster are the same compiled binary, distinguished only by runtime configuration and attestation.*
