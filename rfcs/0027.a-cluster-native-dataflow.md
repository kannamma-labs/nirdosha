# RFC 0027.a: Cluster-native `dataflow!` — scaling by identical processes

Status: **draft / design capture** — a cluster-native amendment to
[RFC 0027](./0027-verified-stream-compute-layer.md). Nothing built.
This document selects external protocols and adapts them to the
Nirdosha v2 Rust dialect, so the stream layer feels as if it was
designed for a cluster from day one.

---

## 1. The two questions this amendment answers

### 1.1 What prevented Nirdosha from supporting cluster/distributed streaming on day one?

The existing RFC 0027 v1 design is intentionally single-node. What is
missing is not language syntax or operator semantics — those are already
cluster-compatible — but the *inter-node substrate*:

| Missing capability | Why v1 does not have it | What the cluster extension must supply |
|---|---|---|
| **Partitioned durable log with consumer groups** | v1 uses an embedded in-process `DurableLog` | A source whose partitions can be split across identical processes, with rebalancing on membership change |
| **Partition assignment / membership** | No concept of a process fleet | A group-membership service; adding/removing a node changes source-partition ownership |
| **Cross-node shuffle / repartitioning** | All edges are local bounded channels | A network backplane that carries keyed records between nodes while preserving total order per partition |
| **Distributed exactly-once commit** | Sinks commit a local offset | Cluster-wide atomic offset+effect commit (provider transaction or self-contained consensus) |
| **Partitioned state backend + migration** | Keyed state is in-process | Snapshots and changelog replay bound to a partition so a reassigned partition can restore on a new node |
| **Global barrier / watermark alignment** | v1 is single input pipe | Coordination across nodes so multi-input joins/windows see aligned watermarks |
| **Authenticated node identity** | Runtime has user/session identity only | Node-to-node identity, mTLS, attestation so untrusted binaries cannot join the group |
| **Cluster-scaled evidence for guarantees** | `V2_GUARANTEES.md` evidence is per-node | Whole-topology, cross-node proofs/certificates for `deterministic_execution`, `durable_transactions`, `authenticated_identity`, `build_provenance`, `deadlock_freedom` |

Rust itself only supplies the *local* substrate: `tokio`, bounded
channels, threads, ownership. It does not provide consumer groups,
partition assignment, distributed logs, membership gossip, or distributed
transactions. Those have to be composed from external systems or built
as part of the runtime.

### 1.2 What already supports clustering today?

RFC 0027's v1 design was built so that clustering is a deployment change,
not a language change:

- **Pure, deterministic operators** — the core semantic unit. They
  commute with replay, so any node can reconstruct any partition's state
  from the log.
- **`#[contract(effects(pure), deterministic)]`** — checked by the
  macro's fast scan and by the rustc driver's resolved-`DefId`
  determinism pass; bans wall-clock, OS entropy, unseeded RNG, and
  ambient mutation.
- **Seeded RNG per record** — `rand_*` kernels derive seeds from the
  source log offset, so replay is byte-identical across nodes.
- **Key-partitioned routing** — the `keyed(by = "...")` operator is a
  declared partition key; it maps directly onto log partitions and
  repartition topics.
- **Bounded-channel edges** — local backpressure; the same shape survives
  as local inlets/outlets in a cluster process.
- **Logical-time watermarks** — derived from source offsets and declared
  `event_time` fields, with no `Instant`; the same model scales to
  per-partition watermarks.
- **Affine state handles** — `StateHandle<K,V>` has an acquire → snapshot
  → release lifecycle, the right shape for moving a partition's state
  between nodes.
- **`exactly_once` sink commit order** — the driver's
  `commit_order` pass proves the local offset commit dominates the
  effect; the cluster extension only has to make the offset durable and
  replicated.
- **Uniform provider model (RFC 0011)** — sources and sinks are already
  abstracted as provider-backed ports; a Kafka-compatible log is just
  another provider.
- **Structured concurrency (RFC 0006)** / APM kernel (RFC 0007) — the
  runtime already has bounded, admission-controlled tasks; cluster
  processes reuse the same `Domain` ceilings.

In short: the *language* and the *single-node runtime* are already
cluster-shaped. What this amendment adds is the *distributed backplane*
and the *operational model* for identical processes.

## 2. Design principle: one process is a one-member cluster

The cluster-native design rejects the Flink "JobManager + TaskManager"
dichotomy. Every Nirdosha process runs the **same compiled topology**,
carries the **same certificate/guarantee bundle**, and participates in the
**same consumer group**. A single-process deployment is simply a group
with one member. Adding a node means starting another identical process
with the same `group_id`, `cluster_seed_nodes`, and attested binary.

Consequences:

- No special roles, no leader election on the hot path.
- Source partitions are the unit of work distribution.
- Removing a node is a consumer-group rebalance; the partitions it owned
  are replayed on the surviving members from the last committed offset.
- The `dataflow!` macro, contract syntax, and driver passes do not
  change. Clustering is expressed in **runtime configuration** and
  **provider URLs** only.

---

## 3. The cluster backplane: a partitioned durable log

The recommended first backplane is an **external Kafka-compatible log**
(Redpanda, Kafka, or any provider implementing the same protocols).
This is the fastest path to a real cluster because it buys:

- durable, replayable, offset-ordered partitions;
- consumer-group membership and partition assignment (KIP-848
  incremental cooperative rebalance);
- idempotent/exactly-once producers and transactions;
- compacted changelog topics for state stores;
- a mature operational ecosystem.

The v1 `DurableLog` is generalized behind a `LogProvider` trait with two
initial implementations:

| Provider | Mode | Use |
|---|---|---|
| `EmbeddedLog` | single-node | v1 default; the topology runs embedded in one process |
| `KafkaLog` | cluster | the topology runs as a consumer group over external partitions |

Selection is runtime configuration (`--source-provider=kafka://...` or
`env`), never source syntax. The `dataflow!` source declaration stays:

```rust
source ledgerlog: DurableLog<LedgerTxn> = "ledger";
```

The runtime maps the logical source name `ledger` to the configured
provider topic.

A future **self-contained mode** can replace `KafkaLog` with a Nirdosha-
owned Raft+SWIM stack (§10). The surface is unchanged because both
implement the same `LogProvider` trait.

## 4. Topology execution in a cluster

### 4.1 Source partition ownership

Each process is assigned a subset of source partitions by the consumer
group. A process reads only its assigned partitions and runs a local
copy of the full topology for each partition it owns. Keyed operators
route records to the same partition for the same key at the source; if a
subsequent operator needs a different grouping, the runtime emits a
**repartition topic**.

### 4.2 Local edges vs. cross-node edges

- **Local edges** remain bounded channels, exactly as in v1.
- **Cross-node edges** are realized by writing to a repartition topic in
  the shared log. The upstream operator appends keyed records; the
  downstream operator reads the partitions assigned to its node.

This design keeps the network coupling minimal: there is no direct
node-to-node socket mesh. Backpressure is preserved by a **credit-based
in-flight cap** over the log: the runtime pauses polling from a source
partition when the local downstream mailboxes are full, and pauses
producing to a repartition topic when uncommitted, unacked records
exceed a bound. The log itself is the buffer, bounded by retention and
credit.

### 4.3 Determinism under rebalance

When a node joins or leaves:

1. Group rebalancing revokes some partitions from existing members.
2. Revoked members finish records up to the next barrier, snapshot their
   partition state, and commit the final offset.
3. New members (or surviving members taking over partitions) restore
   from the snapshot and replay from the committed offset.

Because operators are deterministic and RNG is offset-seeded, replay
reproduces the same state. The proof obligation is unchanged: the
driver's determinism pass and the seeded-RNG discipline make
partition migration a replay problem, not a consensus problem.

## 5. State management

### 5.1 Per-partition keyed state

`StateHandle<K,V>` is scoped to a **partition**, not a process. Within
a process, each owned partition gets its own handle namespace. The
runtime isolates partition states so a rebalance moves only the
reassigned partitions.

### 5.2 Snapshots and changelog

Each partition's state is snapshotted on barrier completion. The runtime
writes:

- **state snapshots** to a changelog topic (compacted) or to a
  provider-supported KV/object store;
- **offsets** to the consumer group's standard offset store;
- a **snapshot metadata record** linking offset → snapshot version.

Restore is: load latest snapshot ≤ committed offset, then replay from
snapshot offset to committed offset. Because operators are pure,
replaying the same records yields the same state deterministically.

### 5.3 Single-node fallback

In `EmbeddedLog` mode, snapshots are local files; the cluster machinery
is simply absent. The same state-handle code path is used, so testing a
single-node topology exercises the same checkpoint/restore logic that a
cluster process uses.

## 6. Logical time and barriers

### 6.1 Watermarks

Each source partition emits watermarks derived from its own offsets and
declared `event_time` field. The runtime advances a **per-partition
watermark** and, where needed, a **combined watermark** for
multi-input operators. Windows fire when the combined watermark passes
their bound, not when wall-clock time elapses.

### 6.2 Barriers

A **barrier** is a control record injected into every source partition.
A process completes the barrier for a partition when it has processed
all data records before the barrier in that partition. Cluster-wide
barrier completion is the conjunction across all partitions owned by the
process and, for multi-input operators, across all input partitions.

Barriers drive:

- state snapshots;
- watermark advancement;
- exactly-once sink alignment.

Barrier injection can be performed by any process after a pre-defined
offset interval or by an optional lightweight coordinator. The
protocol is log-based, not RPC-based, so it does not require a stable
leader on the hot path.

### 6.3 Multi-input joins and windows

Multi-input operators (joins, session windows) are intentionally
**out of the first cluster milestone**. They require global watermark
alignment and repartitioning on a common join key; the design above
supports them, but the driver/runtime proof that alignment is correct
across nodes is left for a later phase.

## 7. HTTP ingress, sinks, and node failures

This section answers the operational questions that come up immediately
once a topology is no longer a single process: *When a REST API is
called, where does it run? What if that machine disappears in the
middle? Is everything a separate process with RPC?*

### 7.1 There is no RPC between operators or between nodes

The cluster model is **log-backed, not RPC-backed**:

- **Inside one process**, operators are the same local tasks/mailboxes
  RFC 0027 v1 describes. They communicate over bounded channels.
- **Across processes**, they communicate by reading and writing
  partitions in the shared durable log. A record produced on node A is
  consumed on node B only when node B polls its assigned partition.

There is no direct node-to-node socket mesh, no gRPC/HTTP service calls
between operators, and no per-operator process. The only cross-process
"wire" is the log.

### 7.2 Where a webhook/REST source runs

In RFC 0027 v1 a `HttpWebhook<T>` source is a route in the compiled
`serve` router. In cluster mode that route exists in **every process**,
so any node can receive a webhook POST. A load balancer in front of the
fleet distributes calls; the process that receives the POST is the one
that ingests it.

The route handler does two things, in order:

1. **Append the event to the shared durable log** under the source's
   topic, using the log's idempotent producer with an idempotency key
   derived from a caller-supplied header or request fingerprint.
2. **Return HTTP 202 Accepted** once the append is acknowledged by the
   log provider (i.e., durably replicated to its configured replication
   factor).

The synchronous HTTP call therefore ends at the log, not at the first
operator. The caller has a deterministic answer: the event is durable
or it isn't. Actual stream processing happens asynchronously from the
log.

This is the same outbox/relay shape RFC 0027 describes for exactly-once
side effects, but turned inside-out: the webhook is the *ingress* side
of the same durable log.

### 7.3 Where the rest of the topology runs

After the event is in the log:

- The **consumer group** decides which partitions each node owns.
- A node runs a **local topology executor** for every partition it
  owns. That executor contains the same operator graph as every other
  node.
- Keyed operators, windows, and sinks run inside that executor. Their
  state is scoped to the partition they are processing.

So if a webhook POST lands on node A but the partition for that event's
key is owned by node B, the flow is:

```
POST -> node A serve router
  -> append to log partition P
node B polls partition P
  -> runs enrich / by_account / window / sink
```

The caller never sees this routing; it only sees HTTP 202.

### 7.4 What happens when a machine becomes unreachable

There are four failure windows, and each has a defined answer.

**Case 1: node dies before returning HTTP 202.**
The caller sees a timeout or connection error and retries. Because the
log producer is idempotent (keyed by the caller's idempotency key), a
retry does not create a duplicate event. Ingestion is therefore
**at-least-once** at the network level, but the log itself is
idempotent.

**Case 2: node returns HTTP 202 but dies before the event is fully
replicated by the log provider.**
This is the log provider's durability contract. With replication
factor 3, a 202 means the provider has acknowledged the write to enough
replicas; the provider (Kafka/Redpanda) is responsible for surviving this
node's death. Nirdosha does not add a second guarantee on top of the
provider's.

**Case 3: event is in the log, but the processing node dies.**
The consumer group detects the failed member (via provider session
timeout in the external mode, or via SWIM in the self-contained mode).
The partitions the dead node owned are reassigned to surviving nodes.
Each new owner:

- loads the latest snapshot for that partition (≤ last committed offset);
- replays the log from the snapshot offset to the committed offset;
- resumes processing new records.

Because operators are deterministic and RNG is offset-seeded, replay
reconstructs the exact same state. The topology continues as if the
node had merely paused.

**Case 4: a sink effect is in flight when the node dies.**
For an `exactly_once` sink, the commit order is:

```
offset_commit(partition, offset)  -> durable in log transaction
sink effect                         -> idempotent under exactly_once.key
```

If the node dies *between* offset commit and effect, replay from the
committed offset re-drives the sink. The `exactly_once.key` deduplicates
the second attempt, so the external effect happens once.

If the node dies *before* offset commit, replay resumes before the
sink call and the effect is not yet visible externally.

For an `at_least_once` sink, duplicates are possible; the downstream
system must tolerate them or the operator must provide its own
idempotency.

### 7.5 REST API sinks

A sink that calls an external REST API is an `effects(http)` side
effect. The call runs inside the process/operator that owns the
partition for that record. It uses the uniform provider model from
RFC 0011, so the same `call_via`/`http_post` semantics apply, including
admission ceilings and rehydration.

If the node dies during the HTTP call, the partition is replayed on a
new node and the call is reissued. This is why `exactly_once` sinks
require an idempotent external API or an idempotency key the provider
understands.

### 7.6 Operational summary

| Concern | Answer |
|---|---|
| Is every operator a separate process? | No — operators are local tasks inside a process. |
| Is there RPC between nodes? | No — cross-node traffic goes through the shared log. |
| Where does a webhook run? | On whichever node receives the HTTP POST; it only appends to the log. |
| Where does processing run? | On whichever node owns the relevant log partition. |
| What if the HTTP node dies before 202? | Caller retries; log producer deduplicates by idempotency key. |
| What if the processing node dies? | Partition reassigned; new node restores snapshot + replays. |
| What if the sink node dies mid-effect? | `exactly_once` key deduplicates on replay; `at_least_once` may duplicate. |

## 8. Exactly-once sinks in a cluster

The local proof from RFC 0027 is preserved: the driver checks that the
sink's offset commit dominates the effect. In cluster mode the runtime
extends this to a **distributed two-phase commit**:

1. Within a sink operator, call `offset_commit(partition, offset)` before
   the effect, keyed by the declared `exactly_once.key`.
2. The runtime records the `(partition, offset, key)` tuple as part of
   the provider transaction (Kafka transaction or self-contained Raft
   log).
3. The effect is idempotent under the same key.
4. The transaction commits atomically with the log offset.

If the process crashes between offset commit and effect, replay from the
committed offset is idempotent because the key de-duplicates the second
attempt. The driver's `commit_order` pass still guarantees the local
ordering; the provider transaction guarantees cluster-wide atomicity.

`at_least_once` sinks skip the transaction and rely on key deduplication
only.

## 9. Membership, failure detection, and node identity

### 9.1 Group membership

Cluster processes discover each other through a small set of **seed
nodes**. Membership state is maintained by **SWIM gossip** (or, in the
external-provider mode, by the log's own consumer group metadata). SWIM
provides:

- failure detection without a central coordinator;
- symmetric, identical processes — no task-manager/worker split;
- bounded false-positive rate and quick convergence.

The provider-backed mode can rely on the consumer group alone; the
self-contained mode needs SWIM (or equivalent) plus a local partition
assignment protocol.

### 9.2 Node identity and attestation

A node must present a **verified identity** before it is admitted to the
group, consistent with Row 12 (`VerifiedIdentity`, `RoleView`) and
`docs/goal.md` row 10. The attestation chain includes:

- mTLS certificate or token issued by the operator's identity provider;
- a certificate/guarantee bundle for the running binary;
- matching `group_id` and `cluster_id`.

The runtime refuses to join a group whose binaries fail the bundle
audit, preserving `build_provenance` across the fleet.

---

## 10. A future self-contained mode: Raft + SWIM

The recommended first implementation uses an external provider because
it lets Nirdosha validate language/runtime guarantees before building
consensus infrastructure. A self-contained mode is designed but not
dependent on it:

- **SWIM gossip** handles membership and failure detection.
- **Raft** (or a variant) replicates a small cluster metadata log:
  group membership, partition-to-node assignments, barrier control
  records, and offset commits.
- The **data plane** still uses the `LogProvider` trait; the Raft log is
  one implementation.
- State snapshots can be stored locally or in a shared object store;
  replay from the replicated log reproduces state on any node.

This mode lets Nirdosha ship a cluster without an external dependency,
but it is strictly later. The surface does not change.

## 11. Effect on v2 guarantees

`docs/V2_GUARANTEES.md` requires cluster-scaled evidence for several
semantics. This amendment maps each to the proposed mechanisms:

| Guarantee | Per-node evidence today | Cluster-scaled evidence needed | Mechanism in this design |
|---|---|---|---|
| `deterministic_execution` | Seeded RNG, no wall-clock, driver determinism pass | Replay across rebalanced partitions produces identical state | Partition-scoped state + snapshot + offset-seeded replay |
| `durable_transactions` | WAL/idempotent retries in `DurableSaga` | Cross-node atomic offset+effect commit | Provider transactions or Raft metadata log + idempotent sink keys |
| `authenticated_identity` | User/session role proofs | Node identity and binary attestation | mTLS/tokens + guarantee-bundle audit at join time |
| `build_provenance` | Per-package certificate/bundle | Fleet-wide attestation that every node runs the same binary | Same `group_id` + bundle hash check + signed manifests |
| `deadlock_freedom` | Bounded local channels, dynamic stall detector | Cluster-wide progress argument; no distributed locks | Credit-based backpressure, DAG topology, log as the only cross-node coupling |

The certificate's `dataflow` section (already planned in RFC 0027)
gains cluster fields: `provider`, `group_id`, `partition_count`,
`exactly_once_mode`, `snapshot_backend`. The driver checks are unchanged
because the language surface is unchanged; the new evidence is
runtime/operational.

## 12. Implementation phases

These phases follow RFC 0027 v1 but re-frame them for cluster-native
deployment. A single-node deployment is Phase 0 only.

### Phase 0 — Provider-agnostic `LogProvider` abstraction

- Generalize the v1 `DurableLog` into a `LogProvider` trait:
  `read_partition`, `append`, `commit_offset`, `list_partitions`,
  `snapshot_topic`.
- Implement `EmbeddedLog` (single-node, local file) first so all
  existing v1 tests run unchanged.
- Add runtime configuration for provider URL, `group_id`,
  `cluster_id`, seed nodes.

### Phase 1 — Consumer group + per-partition executor + HTTP ingress

- Add `KafkaLog` implementation behind the `LogProvider` trait.
- Run one local topology executor per assigned partition.
- Implement partition ownership lifecycle: assign, revoke, finish
  in-flight, commit offset; restore on rebalance from committed offset.
- Wire `HttpWebhook` sources to append to the shared log and return
  HTTP 202 once the append is durable. Document idempotency-key
  conventions for callers.
- Add cluster-health metrics and a CLI `nirdosha-rt dataflow cluster
  status`.

### Phase 2 — Repartition topics and cross-node shuffle

- Emit keyed repartition records from upstream operators whose
  downstream operator has a different `keyed(by = ...)` key.
- Read assigned repartition partitions into the local topology.
- Enforce credit-based in-flight cap to preserve bounded-mailbox
  backpressure.

### Phase 3 — Partitioned state snapshots + restore

- Snapshot keyed state per partition on barrier.
- Write snapshots to provider changelog topic or object store.
- Restore from snapshot + replay on rebalance.

### Phase 4 — Global barriers and multi-input windows

- Coordinate barrier injection across all source partitions.
- Implement combined watermarks for multi-input operators.
- Add driver/runtime checks that multi-input operators declare
  compatible watermarks.

### Phase 5 — Self-contained Raft+SWIM mode

- Implement SWIM membership.
- Implement Raft metadata log.
- Provide a `RaftLog` `LogProvider` implementation.
- Add node identity and guarantee-bundle fleet attestation.

## 13. Open decisions

1. **Initial provider**: external Kafka-compatible (recommended) vs.
   self-contained Raft from day one? The external path lets guarantees
   and the runtime mature first.
2. **First milestone scope**: single-input/stateful-per-partition
   topologies only, or include repartitioning + joins immediately?
   Recommended: single-input first.
3. **Snapshot backend**: provider changelog topics, a separate KV/object
   store, or an embedded guard-store topic? Recommended: provider
   changelog topics for the external mode; local RocksDB + shared
   object store for self-contained mode.
4. **Barrier coordinator**: any process can inject barriers from a
   pre-defined offset interval, or a lightweight elected coordinator?
   Recommended: log-based, any process, with a deterministic interval
   derived from `max_records_per_barrier`.
5. **Multi-input join order**: guarantee that watermark alignment is
   monotonic and complete across partitions — needs a separate
   driver proof.

---

## 14. Rejected alternatives

- **Flink-style JobManager/TaskManager split.** Violates the principle
  of identical processes and adds a new role that would need its own
  attestation and failure model.
- **RPC or direct node-to-node calls between operators.** RPC couples
  sender and receiver lifetimes, complicates retry/timeout semantics,
  and makes node failure harder to reason about. The shared log is the
  only cross-node coupling; records are consumed by polling, not by
  calls.
- **Direct node-to-node TCP mesh for shuffle.** Complicates backpressure,
  membership, and firewall rules; the shared log gives the same
  semantics with a single external coupling.
- **Building a self-contained consensus layer first.** Slower to validate
  and does not leverage existing KIP-848/Redpanda operational maturity.
- **Changing `dataflow!` syntax for clustering.** Clustering is a
  deployment/runtime concern; the language surface stays the same so
  certificates and driver checks remain unchanged.

---

## 15. Relationship to other RFCs

- **RFC 0027** — this document amends it; v1 single-node design is
  retained as `EmbeddedLog`.
- **RFC 0011** — `LogProvider` is a provider behind a port; the same
  two-driver rule and credential-stripped identity apply.
- **RFC 0006** — per-partition executors use the same structured
  concurrency primitives; the dynamic stall detector extends naturally
  to detecting local deadlocks inside a partition executor.
- **RFC 0007** — the APM kernel's `Domain` ceilings apply per process,
  per partition; cross-node traffic is charged against the log provider
  domain.
- **RFC 0017** — the guarantee manifest gains cluster fields; fleet
  attestation is a new kind of evidence.

---

*This amendment keeps the v1 language and verification intact and
adds only a distributed backplane. The goal is that a single-process
`dataflow!` program and a twenty-process cluster are the same compiled
binary, distinguished only by runtime configuration and attestation.*
