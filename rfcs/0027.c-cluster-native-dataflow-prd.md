# RFC 0027.c: Cluster-native `dataflow!` — final PRD

Status: **merged / implementation-ready PRD**. This document supersedes the draft capture in [RFC 0027.a](./0027.a-cluster-native-dataflow.md) and the intermediate merge in [RFC 0027.b](./0027.b-cluster-native-dataflow-merged.md). It selects the best-practical alternatives from the multi-agent critique, resolves cross-theme tensions, pins the operational parameters left open in prior rounds, and maps every acceptance criterion to the project’s stated rubric.

> **Rubric anchoring (Vision):** *Practical* — reuses the v1 `dataflow!` surface, the `nirdosha-rt` runtime-kernels, and `cargo nirdosha verify`; *Grounded* — inherits RFC 0027, RFC 0011, RFC 0017, `docs/V2_GUARANTEES.md`, `docs/KUBERNETES.md`, `docs/adr/0016`, and the existing `crates/nirdosha-ingestion-topic-kafka` driver; *Innovative* — cluster scale without JobManager/TaskManager-style special roles, using a log-backed, identical-process model.

---

## 1. Vision

Nirdosha stream-compute topologies are today confined to a single OS process. The `dataflow!` surface, deterministic-operator contract, seeded RNG, bounded local channels, affine `StateHandle`s, and per-node `DurableLog` already give the *language* a cluster-compatible shape, but there is no inter-node substrate to make one process and many processes the same deployment artifact. This RFC closes that gap.

The goal is a cluster-native `dataflow!` runtime extension where the **same compiled binary** runs on one process or on a fleet of identical processes, distinguished only by runtime configuration and attestation. Adding or removing a node changes **only source-partition ownership** inside a single consumer group; a failed node’s partitions resume elsewhere by **restoring the latest snapshot and replaying from the committed offset**, reconstructing byte-identical state because operators are deterministic and RNG is offset-seeded. HTTP/webhook ingress, repartitioning, state snapshots, barriers, watermarks, and exactly-once sinks are all mediated through a **shared durable log**; there is no direct socket mesh or RPC between operators or between nodes. Every `V2_GUARANTEES.md` guarantee — `deterministic_execution`, `durable_transactions`, `authenticated_identity`, `build_provenance`, `deadlock_freedom` — is evidenced at **fleet scale**, not just per-node.

This is **not** a new language syntax project. The `dataflow!` macro, `#[contract(..)]`, and driver passes remain unchanged. Clustering is expressed through runtime configuration, provider URLs, a signed fleet manifest, and the certificate/guarantee bundle.

---

## 2. Goals

1. **Identical-process deployment.** Every process runs the same compiled topology; a single process is a one-member cluster.
2. **Partition-ownership work distribution.** Source partitions are the unit of work; the log’s consumer-group protocol decides which process owns which partition.
3. **Log-backed cross-node shuffle.** Repartitioning and cross-node traffic happen only through the shared durable log.
4. **Deterministic replay after failure.** Rebalance/failover restores partition state from snapshots and replay; operators are pure and RNG is offset-seeded, so state is byte-identical across nodes.
5. **Exactly-once sinks at fleet scale.** Offset commit dominates the sink effect; provider transactions or idempotent sink keys make the external effect appear once.
6. **Fleet-scale v2 guarantees.** Static fleet guarantee bundles, a signed operator manifest, and runtime enforcement hooks provide evidence for all five cluster-scaled guarantees.
7. **Single-node compatibility.** `EmbeddedLog` mode keeps today’s single-node tests running unchanged.
8. **Falsifiable fleet behavior.** A `SimulationLog` harness implements the `LogProvider` trait and asserts the invariants a real cluster must satisfy, so fleet-scale evidence can be exercised in CI before a production broker is involved.

---

## 3. Non-goals

1. **Multi-input joins and session windows** are **out of the first milestone** (Phases 0–3). The design must not foreclose them, but the driver/runtime proof of global watermark alignment for joins is deferred to Phase 4.
2. **Self-contained consensus** (Raft + SWIM) is a future Phase 5 track; Phases 0–3 target an external Kafka-compatible log.
3. **Native iOS/Android generation** from dataflow topologies is out of scope.
4. **Changing `dataflow!` syntax** for clustering — the surface stays the same.
5. **Guaranteeing exactly-once to arbitrary non-idempotent external APIs** — the runtime can only guarantee this when the sink target is listed in `provider_capabilities.json` or the operator supplies a proven idempotency mechanism.
6. **Provider-independent exactly-once transactions** — the first milestone requires a provider that supports either native producer transactions or a control-log+offset atomic commit.

---

## 4. The chosen innovations

Each subsection specifies the mechanism, data/control flow, interfaces, and key behaviors. Residual ambiguity is marked `OPEN QUESTION:` explicitly.

### 4.1 Dual-use `LogProvider`: runtime trait + deterministic cluster simulator

#### Mechanism

The v1 embedded `DurableLog` is generalized behind a `LogProvider` trait. The same trait is implemented by a real provider **and** by a deterministic in-memory simulator, so the topology and the cluster invariants can be tested without a live broker. Two initial real implementations are required:

| Implementation | Mode | Backing store |
|---|---|---|
| `EmbeddedLog` | single-node | Local files + SQLite offset store |
| `KafkaLog` | cluster | External Kafka/Redpanda topic |

Selection is runtime configuration, never source syntax. The `dataflow!` source declaration stays:

```rust
source ledgerlog: DurableLog<LedgerTxn> = "ledger";
```

The runtime maps the logical source name `ledger` to the configured provider topic.

#### `LogProvider` trait contract

```rust
pub trait LogProvider: Send + Sync + 'static {
    /// Static capabilities of this provider. Used by the driver and runtime
    /// to pick exactly-once strategy, snapshot backend, and barrier path.
    fn capabilities(&self) -> ProviderCapabilities;

    /// Partition discovery for a logical topic.
    fn list_partitions(&self, topic: &str) -> Result<Vec<PartitionId>, LogError>;

    /// Poll one source/repartition partition from an explicit offset.
    fn poll_partition(
        &self,
        topic: &str,
        partition: PartitionId,
        from_offset: Offset,
        max_records: usize,
        max_wait_ms: u32,
    ) -> Result<Batch, LogError>;

    /// Append a keyed record to a data topic (source/repartition).
    /// Partition routing is provider-native (Kafka partitioner) or deterministic
    /// (EmbeddedLog). The caller may pass `None` for partition and rely on `key`.
    fn append(
        &self,
        topic: &str,
        partition: Option<PartitionId>,
        key: &[u8],
        value: &[u8],
    ) -> Result<Offset, LogError>;

    /// Append a control record to the shared control topic.
    fn append_control(&self, record: ControlRecord) -> Result<Offset, LogError>;

    /// Commit a consumer offset. For exactly-once this is called inside a transaction.
    fn commit_offset(
        &self,
        topic: &str,
        partition: PartitionId,
        offset: Offset,
    ) -> Result<(), LogError>;

    /// Open a provider transaction. `txn_id` is unique per process/epoch.
    fn open_transaction(&self, txn_id: &str) -> Result<Box<dyn LogTxn>, LogError>;

    /// Snapshot storage backend for this provider.
    fn snapshot_backend(&self) -> Arc<dyn SnapshotBackend>;

    /// Logical name of the single-partition control topic.
    fn control_topic(&self) -> &str;
}

pub trait LogTxn: Send + Sync {
    fn send(
        &mut self,
        topic: &str,
        partition: Option<PartitionId>,
        key: &[u8],
        value: &[u8],
    ) -> Result<(), LogError>;
    fn send_control(&mut self, record: ControlRecord) -> Result<(), LogError>;
    fn commit_offset(
        &mut self,
        topic: &str,
        partition: PartitionId,
        offset: Offset,
    ) -> Result<(), LogError>;
    fn commit(self: Box<Self>) -> Result<(), LogError>;
    fn abort(self: Box<Self>) -> Result<(), LogError>;
}
```

#### `ProviderCapabilities` schema

```rust
pub struct ProviderCapabilities {
    /// How exactly-once sinks are realized.
    pub exactly_once_mode: ExactlyOnceMode,
    /// Whether the provider exposes a durable, single-partition control topic.
    pub control_topic: bool,
    /// Max bytes per append record (snapshot chunking limit).
    pub max_message_size: usize,
    /// Available snapshot backends for this provider.
    pub snapshot_backends: Vec<SnapshotBackendKind>,
    /// Provider-side idle session timeout in milliseconds.
    pub idle_timeout_ms: u64,
}

pub enum ExactlyOnceMode {
    /// Native producer transactions commit offset + SinkIntent atomically.
    ProviderTransaction,
    /// No provider transactions; exactly-once relies on control-log
    /// SinkIntent + idempotent sink key only.
    SinkKeyOnly,
}
```

#### `SimulationLog`

`SimulationLog` is an in-memory `LogProvider` used in deterministic tests and in `cargo nirdosha verify --sim-cluster`. It asserts the following invariants on every operation:

- A process may poll only partitions the provider has assigned to it.
- Cross-node traffic is visible only as keyed records in repartition topics; there is no direct message-passing channel between simulated processes.
- Every control record is observed by all simulated processes in the same total order.
- `BarrierTimeout` tie-breaking uses the canonical rule from §4.5, not per-process wall-clock observation.
- Credit ledgers never go negative and stale grants are invalidated deterministically (§4.3).
- Snapshot `state_hash` round-trips: a restored partition must produce the same `state_hash` after replay.

The simulator is not a replacement for real broker testing, but it makes the fleet-scale invariants **falsifiable** in ordinary unit tests.

> **Rubric anchoring (4.1):** *Practical* — reuses the v1 `DurableLog` shape and the `rskafka`-based `KafkaTopicDriver` from `crates/nirdosha-ingestion-topic-kafka`; *Grounded* — matches RFC 0011 provider model and `docs/adr/0016`; *Zero-ambiguity* — the trait pins `capabilities()`, snapshot backend, control topic, and credit flow; *Innovative* — a log-provider trait whose test implementation is a deterministic cluster simulator.

### 4.2 Identical-process execution model and partition ownership

#### Mechanism

Every process runs the **full compiled topology**, but only over the source partitions it currently owns. Each owned partition gets its own local executor containing the same operator graph. Local edges remain bounded channels, exactly as in v1.

Membership and partition assignment use the **provider-native consumer group** in external mode (Kafka/Redpanda KIP-848 incremental cooperative rebalance). The self-contained mode (Phase 5) layers SWIM + Raft behind the same `LogProvider` trait; the surface is unchanged.

#### Deterministic handoff lease

On graceful revocation, the old owner writes a `PartitionHandoff` control record after draining in-flight work to the next barrier:

```rust
ControlRecord::PartitionHandoff {
    epoch: u64,
    source_topic: String,
    partition: PartitionId,
    final_offset: Offset,
    snapshot_key: SnapshotKey,
    handoff_key: String, // deterministic idempotency key
}
```

The `PartitionHandoff`, the source offset, and the corresponding `SnapshotMeta` are committed inside the **same provider transaction**. The `handoff_key` is deterministic: `sha256(topic || partition || epoch || final_offset)` truncated to 32 bytes. Because the single-partition control topic provides a total order, all processes observe the handoff at the same logical point.

#### Rebalance lifecycle

- **On assignment:** the new owner loads the latest `SnapshotMeta` whose `offset ≤ committed_offset`, restores the state, replays from the snapshot offset to the committed offset, then resumes live polling.
- **On revocation:** the old owner stops polling the revoked partition, drains in-flight records to the next barrier, writes a `SnapshotMeta` + `PartitionHandoff`, commits the offset in the provider transaction, then releases the partition. After the transaction commits, the old owner must not produce to repartition topics for that partition and must not perform sink effects for it.
- **On abrupt failure:** the provider consumer group detects the dead member via session timeout and reassigns the partition. A new owner restores from the latest durable `SnapshotMeta` (or the handoff, if present) and replays from its offset to the committed offset.

#### Key behaviors

- There is **no direct node-to-node socket mesh**, no gRPC/HTTP between operators, and no per-operator process.
- The consumer group is the source of truth for partition ownership; the `PartitionHandoff` is a deterministic synchronization point, not the ownership proof.
- Because operators are deterministic and RNG is offset-seeded, replay from any committed offset reconstructs identical state.

> **Rubric anchoring (4.2):** *Practical* — reuses KIP-848 consumer groups rather than building new consensus; *Performant* — poll-based data path with no synchronous cross-node coordination; *Zero-ambiguity* — handoff record, transaction boundary, and session-timeout failure window are pinned; *Grounded* — aligns with RFC 0027.a §4, RFC 0027.b §4.1/§4.2, and `docs/adr/0016`.

### 4.3 Cross-node shuffle and control-topic credit tokens

#### Mechanism

When an upstream operator has a different `keyed(by = "...")` key from its downstream operator, the runtime emits **keyed repartition records** to a compacted repartition topic. The downstream operator consumes only the repartition partitions assigned to its node.

#### Deterministic routing

The repartition partition for a key is computed deterministically:

```text
repartition_partition = fnv1a_64(canonical_key_bytes, cluster_id_seed) mod repartition_partition_count
```

- `canonical_key_bytes` is the `CanonicalBytes` serialization of the declared key field(s) (§4.4.1).
- `cluster_id_seed` is the first 8 bytes of `sha256(cluster_id)`.
- `repartition_partition_count` is a compile-time topology parameter.

Changing `repartition_partition_count` breaks state continuity; it requires a new topology version.

#### Control-topic credit protocol

Backpressure across the log is implemented with explicit **credit tokens** written to the control topic. The downstream owner of a repartition partition grants credits to upstream producers; producers pause when credit reaches zero.

```rust
ControlRecord::CreditGrant {
    epoch: u64,
    repartition_topic: String,
    partition: PartitionId,
    grant_sequence: u64,       // monotonic per (epoch, topic, partition)
    grant_size: u64,             // max records this grant allows
    lease_deadline_epoch: u64,   // epoch by which unreturned credit is reclaimed
    grant_key: String,           // deterministic idempotency key
}

ControlRecord::CreditReturn {
    grant_key: String,
    returned_count: u64,
    return_key: String,          // deterministic idempotency key
}

ControlRecord::CreditRevoke {
    epoch: u64,
    repartition_topic: String,
    partition: PartitionId,
    grant_key: String,
    reason: RevokeReason,        // rebalance | barrier_timeout | lease_expired
}
```

#### Pause/resume triggers

Each producer keeps a per `(repartition_topic, partition)` ledger:

- `available_credit = sum(unrevoked grant sizes) - in_flight_records`.
- When `available_credit == 0`, the producer **stops appending** to that partition. Backpressure propagates upstream through the bounded local mailboxes.
- When the producer receives a `CreditReturn` or a new `CreditGrant`, it resumes appending.
- The producer increments `in_flight_records` when it appends a record and decrements it when it observes the corresponding `CreditReturn` in the control topic.

#### Stale-grant invalidation and leak recovery

- On **rebalance**, the new owner of a repartition partition issues `CreditRevoke` for all grants from the previous epoch, then issues fresh `CreditGrant`s.
- On **barrier timeout**, all unreturned credit for grants whose `lease_deadline_epoch` has passed is revoked and re-granted.
- `CreditGrant` idempotency keys are deterministic and scoped to epoch, so duplicate grants/returns from a restarted producer are provider-deduplicated.
- If a `CreditReturn` is lost, the lease timeout reclaims the credit; the producer may have over-sent, but repartition records are idempotent by key, so duplicates are harmless.

#### Grant sizing

`grant_size C` is derived from the downstream bounded mailbox capacity `M` and the expected fan-in `F`:

```text
C = floor(M / F)
F = max(1, source_partition_count / repartition_partition_count)
```

`max_in_flight_repartition` bounds total in-flight records per repartition partition across all producers: `sum(grant_sizes) ≤ max_in_flight_repartition`.

> **Rubric anchoring (4.3):** *Practical* — built on the existing `__nirdosha_control` topic and bounded-mailbox semantics; *Performant* — credit flow is asynchronous and off the hot data path; *Zero-ambiguity* — ledger, grant/return/revoke records, pause/resume triggers, and leak recovery are pinned; *Innovative* — a distributed credit-flow protocol realized entirely over a shared durable log.

### 4.4 Content-addressed state snapshots, restore, and deterministic replay

#### Mechanism

State is scoped **per partition**, not per process. Within a process, each owned partition gets its own `StateHandle<K,V>` namespace keyed by `(topic, partition, epoch)`.

On barrier completion, the runtime:

1. Serializes the partition state to a canonical byte representation (§4.4.1).
2. Writes the bytes to the `SnapshotBackend` asynchronously; the backend returns a content-addressed `SnapshotKey`.
3. Calls `SnapshotBackend::confirm(key)` to ensure the bytes are durable/readable before using the key.
4. Writes a `SnapshotMeta` control record linking `(epoch, offset)` to the `SnapshotKey` and a Merkle root `state_hash`.
5. Commits the source offset inside the same provider transaction that writes `SnapshotMeta`.

Restore is:

1. Read the latest `SnapshotMeta` whose `offset ≤ committed_offset`.
2. Load the referenced snapshot bytes from `SnapshotBackend::read(key)`.
3. If `read` returns `None`, walk the fallback chain of older `SnapshotMeta` records.
4. Replay records from the chosen snapshot offset to the committed offset.
5. Resume live polling from `committed_offset`.

#### `SnapshotBackend` trait

```rust
#[async_trait]
pub trait SnapshotBackend: Send + Sync {
    /// Write bytes and return a content-addressed key. Does not have to be
    /// fully replicated yet; see `confirm`.
    async fn write(&self, bytes: Bytes) -> Result<SnapshotKey, SnapshotError>;

    /// Mark the key as readable/durable. `SnapshotMeta` is committed only
    /// after `confirm` succeeds.
    async fn confirm(&self, key: &SnapshotKey) -> Result<(), SnapshotError>;

    /// Read a snapshot by key. Returns `None` if the key is not yet readable
    /// or has been garbage-collected.
    async fn read(&self, key: &SnapshotKey) -> Result<Option<Bytes>, SnapshotError>;

    /// List candidate snapshot keys for a partition, newest first,
    /// stopping at the retention boundary.
    async fn list_candidates(
        &self,
        topic: &str,
        partition: PartitionId,
        up_to_offset: Offset,
    ) -> Result<Vec<SnapshotKey>, SnapshotError>;
}
```

#### 4.4.1 Canonical deterministic serialization

The runtime serializes the following into a **byte-identical** representation across processes and restarts:

- All `StateHandle<K,V>` entries for the partition.
- All pending sink intents and uncommitted outbox rows.
- Any window/session state held by the runtime.

The canonical format:

1. **Sort all entries** by a stable ordering of keys.
2. **Serialize keys and values** using a schema-driven binary codec:
   - fixed-width integers (little-endian `i64`, `u64`, `i32`, `u32`),
   - length-prefixed byte arrays for strings and blobs,
   - sorted map iteration order,
   - no floating-point values in keys,
   - NaN handling for float values normalized to a single canonical NaN bit pattern,
   - enum variants as discriminant-index-then-payload,
   - no timestamps or wall-clock fields from the host.
3. **Compute a Merkle tree** over the sorted entries; the root is the `state_hash` stored in `SnapshotMeta`.

The compiler backend emits a `CanonicalBytes` trait implementation for every user-defined type that may appear in a `StateHandle`. The driver rejects types containing wall-clock, raw pointers, or other non-deterministic fields from snapshot-eligible state.

#### Lease-availability fallback

If a new owner tries to restore from the latest `SnapshotMeta` but `SnapshotBackend::read` returns `None` (the bytes are not yet readable or have been lost), it retries with exponential backoff:

- initial delay: 100 ms
- max delay: 10 s
- max total wait per key: 30 s

If the key remains unavailable, the runtime consults the fallback chain produced by `list_candidates`. The chain is ordered newest-first and bounded by log retention. If every candidate is unavailable, the runtime replays from the **earliest retained offset** for that partition. This is a liveness fallback, not a correctness fallback: replay is deterministic and idempotent, so state is still reconstructed correctly.

#### Compaction safety rule

Compacted changelog topics and object-store GC must **never discard every snapshot newer than a live committed offset**:

- Retain the latest snapshot for each partition.
- Retain every snapshot whose `offset` is greater than the minimum committed offset across all live consumers in the group.
- GC removes only snapshots whose `offset` is less than `min_live_committed_offset - snapshot_gc_margin`.

For `EmbeddedLog` single-node mode, compaction is local file rotation with the same rule.

#### Key behaviors

- Full snapshots are taken every barrier. Incremental/delta snapshots are explicitly deferred to Phase 4.
- Snapshot bytes are written asynchronously and confirmed before `SnapshotMeta` is committed atomically with the offset.
- Large snapshots are chunked into `max_snapshot_chunk_size = 1 MiB` records; `SnapshotMeta` references the ordered chunk keys.
- A Merkle `state_hash` lets a new owner verify that restored state matches the attested snapshot.

> **Rubric anchoring (4.4):** *Practical* — reuses `wf_outbox` lease semantics and the provider topic model; *Performant* — async snapshot writes, bounded retry/fallback, off the barrier commit path; *Zero-ambiguity* — `SnapshotBackend` trait, `confirm()` boundary, retry/backoff, fallback chain, and compaction safety rule pin the async-availability window; *Grounded* — matches RFC 0027.b §4.4/§5.2, `crates/nirdosha-workflow/src/outbox.rs`, and `crates/runtime-kernels/src/kernel/transact/durable.rs`.

### 4.5 Control-log epochs, wall-clock liveness oracle, and watermarks

#### Mechanism

The deterministic core remains wall-clock-free. A **barrier epoch** is a logical counter that advances per source partition when:

- it has processed `max_records_per_barrier` records, **or**
- a `BarrierTimeout` control record closes the epoch for that partition, **or**
- a membership change forces a drain-to-barrier.

Barriers are records in the single-partition control topic:

```rust
ControlRecord::Barrier {
    epoch: u64,
    source_topic: String,
    partition: PartitionId,
    source_offset: Offset, // all data records up to this offset are in the epoch
}

ControlRecord::BarrierTimeout {
    epoch: u64,
    source_topic: String,
    partition: PartitionId,
    timed_out_partitions: BTreeSet<PartitionId>, // deterministic set, see below
}
```

A process completes a barrier for partition `p` when it has processed all source records in `p` up to `barrier.source_offset`. Multi-input operators (Phase 4) complete a barrier only when all their input partitions have reached it.

#### Wall-clock liveness oracle

A **liveness watch** observes wall-clock *outside* the data path. When a partition has not produced a new record or `Barrier` control record within `max_barrier_idle_ms`, the watch appends a `BarrierTimeout` record to the control topic. Once written, that record is part of the deterministic log and drives identical decisions everywhere.

Wall-clock is **never an input to operator logic or watermark arithmetic**.

#### Deterministic tie-breaking for `BarrierTimeout`

Multiple processes may independently detect the same idle partition and write a `BarrierTimeout`. The payload must be identical so the provider can deduplicate by the deterministic idempotency key.

The `timed_out_partitions` set is computed from the durable control log alone:

```text
timed_out_partitions(p, epoch) = {
    q in source_topic(p) |
    q has not produced a Barrier/BarrierTimeout record for epoch
    and q has not been observed to complete epoch by the consumer group
}
```

Because every process consumes the same control records in the same order, this rule yields the same set on every process. The `BarrierTimeout` idempotency key is `sha256(source_topic || epoch || canonical_set_bytes(timed_out_partitions))`. If two records with different payloads somehow appear, the first in control-log order wins; later records with different payloads are ignored. **A valid cluster configuration must guarantee that duplicates are byte-identical**; non-identical duplicates are a provider/protocol bug surfaced as a runtime fatal error.

#### Watermark computation

- **Per-partition watermark:** the minimum `event_time` of all unclosed records in partition `p` up to the current completed `source_offset`.
- **Combined watermark (Phase 4):** `min(per-partition watermark over all input partitions)`.
- Windows fire when the combined watermark passes their bound, not when wall-clock time elapses.

#### Key behaviors

- Operators never read the control topic, wall-clock, or liveness metadata. The driver treats access to those as impure.
- `event_time` derives only from the declared field in the data record and the source offset.
- Barrier completion triggers state snapshots, watermark advancement, and sink intent alignment.

> **Rubric anchoring (4.5):** *Zero-ambiguity* — barrier records, idle fallback, and deterministic tie-breaking are pinned; *Practical* — grounded in `transact/durable.rs` and `workflow/outbox.rs` lease semantics; *Innovative* — wall-clock confined to a liveness oracle that emits durable control records.

### 4.6 HTTP ingress, exactly-once sinks, and side-effect commit order

#### Mechanism

HTTP/webhook ingress follows the outbox/relay shape already used by `DurableSaga` and `wf_outbox`:

1. Every process exposes the `HttpWebhook<T>` route.
2. A load balancer distributes POSTs across the fleet.
3. The receiving process appends the event to the shared source topic using an idempotent producer keyed by `event_id`.
4. The process returns **HTTP 202 Accepted** only after the log provider acknowledges durable replication to its configured in-sync replicas.
5. Downstream processing is asynchronous from the log.

#### Source-level `event_id`

Every `HttpWebhook<T>` source requires `T` to declare an `event_id: str` field. The `dataflow!` macro expansion and the driver enforce this at compile time. The `event_id` is used as the log append idempotency key when the caller does not supply one.

The caller may override the `event_id` via the request header:

```text
Nirdosha-Event-Id: <opaque id>
```

If the header is absent, the runtime synthesizes an `event_id` from a canonical fingerprint:

```text
fingerprint = sha256(method || " " || path || "\n" || sorted-stable-headers || "\n" || body)
event_id = lowercase-hex(fingerprint)
```

For v1 webhook sources without `event_id`, the macro synthesizes the field and wires the fingerprint; this is a compatibility shim, not the preferred path.

#### `provider_capabilities.json`

The driver statically verifies every `exactly_once` sink against a provider capability manifest:

```json
{
  "version": "1",
  "exactly_once_sinks": {
    "http_post": {
      "idempotency_key_header": "Idempotency-Key",
      "key_source": "sink_intent_id"
    },
    "db_upsert": {
      "key_source": "primary_key_columns",
      "columns": ["alert_id"]
    },
    "kafka_produce": {
      "key_source": "record_key"
    }
  },
  "providers": {
    "kafka": {
      "transactions": true,
      "control_topic": true,
      "snapshot_backends": ["compacted_changelog", "s3"]
    }
  }
}
```

A sink target must be listed with a supported `key_source`, or the operator must supply a proven idempotency mechanism that the driver can verify on every path before the effect.

#### Exactly-once sink commit order

For an `exactly_once` sink within barrier `e`:

```text
1. append SinkIntent { epoch, partition, intent_id } to __nirdosha_control
2. offset_commit(topic, partition, offset) inside the provider transaction
3. perform the external effect keyed by intent_id
4. commit the provider transaction
```

If the process crashes between steps 2 and 3, replay from the committed offset re-drives the sink and `intent_id` deduplicates the second attempt.

If the process crashes before step 2, the effect is not visible externally and replay resumes before the sink call.

`at_least_once` sinks skip the transaction and the intent record; duplicates are possible and must be tolerated or deduplicated by the operator.

#### Key behaviors

- The synchronous HTTP call ends at the log; actual stream processing is asynchronous.
- The 202 is returned only after the provider acknowledges replication to `min.insync.replicas`.
- The log append is idempotent by `event_id`, so caller retry at the network level does not create duplicate records.

> **Rubric anchoring (4.6):** *Practical* — reuses `DurableSaga`/`wf_outbox` lease model and `HttpWebhook` route integration; *Performant* — bounded in-flight caps and build-time idempotency checks; *Zero-ambiguity* — HTTP 202 boundary, event_id/header convention, `provider_capabilities.json` schema, and commit order are pinned; *Grounded* — maps to `docs/V2_GUARANTEES.md` `durable_transactions`, `crates/nirdosha-workflow/src/outbox.rs`, and `crates/runtime-kernels/src/kernel/transact/durable.rs`.

### 4.7 Fleet attestation and node identity

#### Mechanism

Node identity and attestation follow Row 12 (`VerifiedIdentity`, `RoleView`) and the existing guarantee-bundle machinery. The fleet uses a **service-mesh sidecar** for transport identity and an **operator-signed fleet manifest** for cluster membership policy, matching the sidecar stance in `docs/KUBERNETES.md`.

#### Fleet manifest schema

```json
{
  "manifest_version": "1",
  "cluster_id": "payroll-prod",
  "group_id": "payroll-group",
  "provider_type": "kafka",
  "partition_count": 16,
  "exactly_once_mode": "provider_transaction",
  "snapshot_backend": "compacted_changelog",
  "topology_hash": "<hash of compiled topology + compile-time cluster params>",
  "binary_hash": "<sha256 of compiled binary>",
  "provider_capabilities_hash": "<hash of provider_capabilities.json>",
  "allowed_provider_prefixes": ["kafka://"],
  "sidecar_identity": "spiffe://cluster/nirdosha/payroll",
  "public_key": "<operator public key>",
  "signature": "<signature of canonical JSON minus signature field>"
}
```

`topology_hash` covers the compiled topology plus **compile-time** cluster parameters (`partition_count`, `exactly_once_mode`, `snapshot_backend`, `provider_type`). It explicitly excludes runtime-only values such as `provider_url`, `cluster_id`, `group_id`, and credentials. `binary_hash` is the content hash of the running binary. This resolves the contradiction in prior drafts between “same binary hash” and “topology hash includes runtime config.”

#### Verification at startup/join

1. Verify the manifest signature against the configured trust anchor.
2. Recompute `binary_hash` and compare to the manifest.
3. Compare `topology_hash` against the guarantee bundle’s `cluster.topology_hash`.
4. Compare `provider_type`, `partition_count`, `exactly_once_mode`, and `snapshot_backend` against runtime configuration.
5. Verify that `provider_url` matches one of `allowed_provider_prefixes`.
6. If any check fails, the process exits with `AttestationError::FleetManifestMismatch` before joining the provider group.

#### Sidecar and non-mesh fallback

- **Mesh path (Kubernetes):** the service-mesh sidecar (Istio/Linkerd) provides mTLS and workload identity to the broker. The Nirdosha process delegates all outbound Kafka connections to the sidecar; the runtime verifies only the fleet manifest. Broker ACLs allow only sidecars whose identity matches `sidecar_identity`.
- **Non-mesh fallback:** when no sidecar is configured, the runtime loads an operator-issued client certificate and key (`--fleet-mtls-cert-file`, `--fleet-mtls-key-file`) and presents them to the broker. The broker ACL must allow only clients presenting that certificate. This fallback is acceptable for single-node/bare-metal deployments but is not the preferred production path.

#### Runtime deterministic self-check

The deterministic-runtime self-check is a **concrete enforcement mechanism**, not best-effort detection:

- On Linux, each operator worker thread installs a **seccomp-bpf** filter before processing any partition. The filter is loaded from the guarantee bundle’s `syscall_allowlist` and explicitly denies `clock_gettime`, `getrandom`, `gettimeofday`, `nanosleep`, and any other time/entropy/network/file syscalls that operator code must not use. A denied syscall raises `SIGSYS` and aborts the process.
- Runtime threads (log polling, HTTP ingress, control-topic handling) run without the strict filter.
- The driver already rejects `Instant::now`, `std::time`, OS entropy, and unseeded RNG in operators claimed `deterministic`; seccomp is the runtime backstop.

The guarantee bundle records:

```json
{
  "wall_clock_boundary": "liveness_oracle_only",
  "deterministic_enforcement": "seccomp_bpf"
}
```

#### Signed heartbeat

Each process emits a signed heartbeat to the control topic every `heartbeat_interval = 60 s` containing:

- the node’s `binary_hash`,
- the current completed epoch per owned partition,
- a monotonic wall-clock-free sequence number.

This gives operators an audit trail of which binaries were alive when, supporting `build_provenance` and `authenticated_identity` evidence at fleet scale.

> **Rubric anchoring (4.7):** *Practical* — builds on `cargo nirdosha verify`, `check-certificate`, and `docs/KUBERNETES.md`’s sidecar stance; *Performant* — audit is off-path and transport identity is delegated to the mesh; *Zero-ambiguity* — manifest schema, verification steps, sidecar/non-mesh fallback, and seccomp mechanism are pinned; *Grounded* — maps to RFC 0017 §4, `docs/V2_GUARANTEES.md`, `crates/cargo-nirdosha/tests/guarantee_bundle.rs`, and `docs/KUBERNETES.md`.

## 5. Cross-theme integration

This section resolves the tensions between the recommended alternatives.

### 5.1 Wall-clock vs. deterministic execution

**Tension:** The essence forbids wall-clock in operators/watermarks, but barriers need an idle-source liveness trigger.

**Resolution:** Wall-clock is confined to a **liveness oracle** that appends durable control records. Operators and watermark arithmetic consume only log records. The deterministic core is preserved because the liveness watch is a runtime task, not an operator; `BarrierTimeout` records become part of the deterministic log; and seccomp-bpf denies operator threads access to time/entropy syscalls.

### 5.2 Full snapshots vs. bounded hot-path overhead

**Tension:** Full state snapshots every barrier could be expensive.

**Resolution:** Snapshots are written **asynchronously** after barrier completion; only the small `SnapshotMeta` is committed atomically with the offset. Large snapshots are chunked, the format is compact binary, and `max_records_per_barrier` bounds frequency. Incremental/delta snapshots are deferred to Phase 4.

### 5.3 Compile-time idempotency vs. provider transaction

**Tension:** Side-effect verification is compile-time, but the actual distributed commit needs a runtime primitive.

**Resolution:** Layer both. The driver checks `exactly_once` sinks against `provider_capabilities.json`. The runtime uses the provider transaction primitive (`ProviderTransaction` mode) or the control-log `SinkIntent` path (`SinkKeyOnly` mode). The bundle declares which mode is in use so the runtime chooses the right path.

### 5.4 Static bundle vs. runtime attestation

**Tension:** A static bundle can be bypassed by a compromised process that skips the check.

**Resolution:** The fleet manifest check is mandatory at startup and on every join; the runtime exits on failure. Broker-level enforcement (sidecar mTLS / fallback client cert + ACLs) prevents untrusted binaries from joining the group or producing to topics. The seccomp-bpf filter and signed heartbeat provide runtime detection.

### 5.5 Provider-native group vs. self-contained consensus

**Tension:** The first milestone relies on Kafka/Redpanda consumer groups, but the long-term vision is a self-contained Raft + SWIM mode.

**Resolution:** The `LogProvider` trait is the isolation boundary. `KafkaLog` is Phase 0–3; `RaftLog` is Phase 5. Both implement the same trait, so topology source code, driver checks, the bundle, and the simulator remain unchanged.

### 5.6 `topology_hash` vs. runtime configuration

**Tension:** Earlier drafts said `topology_hash` must match the running binary while also defining it as “compiled topology + runtime config,” which is contradictory because `provider_url` and `cluster_id` are runtime-only.

**Resolution:** `topology_hash` covers the **compiled topology + compile-time cluster parameters** (`partition_count`, `exactly_once_mode`, `snapshot_backend`, `provider_type`). Runtime-only values (`provider_url`, `cluster_id`, `group_id`, credentials) are validated separately against the signed fleet manifest. `binary_hash` covers the running binary. The bundle contains both hashes; the runtime checks both.

### 5.7 `SimulationLog` vs. real provider implementations

**Tension:** The simulator is valuable for testing but does not stand alone as a production backplane.

**Resolution:** `SimulationLog` is a test/verification harness layered **on top of** the same `LogProvider` trait that `EmbeddedLog` and `KafkaLog` implement. It is required for CI and for `cargo nirdosha verify --sim-cluster`, but production deployments use a real provider. The simulator’s fidelity to Kafka/Redpanda rebalance and transaction behavior is load-bearing; its assertions must be kept in sync with the real provider semantics.

## 7. Operational scenarios

### 7.1 Node dies before returning HTTP 202

- Caller sees timeout or connection error and retries.
- Log append is idempotent by `event_id`/caller header.
- Result: at-least-once at the network level; the log has exactly one record.

### 7.2 Node returns 202 but dies before provider fully replicates

- The 202 is returned only after the provider acknowledges replication to `min.insync.replicas`.
- Surviving the ingress node’s death is the provider’s durability contract.
- Nirdosha does not add a second guarantee on top.

### 7.3 Event is in the log, but the processing node dies

- Consumer group detects the failed member via provider session timeout (or SWIM in Phase 5).
- Partitions are reassigned to surviving nodes.
- New owner loads the latest snapshot ≤ committed offset, replays to committed offset, resumes live processing.
- Because operators are deterministic and RNG is offset-seeded, state is reconstructed identically.

### 7.4 Sink effect is in flight when the node dies

- For `exactly_once` sinks: `SinkIntent` and offset are committed in the provider transaction before the effect. If the node dies between commit and effect, replay re-drives the sink and `intent_id` deduplicates.
- For `at_least_once` sinks: duplicates are possible; downstream must tolerate them.

## 8. Implementation phases

These phases follow the Track H items in `docs/ROADMAP.md`.

### Phase 0 — `LogProvider` abstraction and simulator

- Define `LogProvider`, `LogTxn`, `SnapshotBackend`, `ProviderCapabilities`, and `ControlRecord`.
- Implement `EmbeddedLog` first; all existing v1 tests run unchanged.
- Implement `SimulationLog` with invariant assertions.
- Add runtime configuration and fleet manifest fields to the guarantee bundle.

### Phase 1 — Consumer group, per-partition executor, HTTP ingress

- Extend `crates/nirdosha-ingestion-topic-kafka` for multi-partition topics, consumer groups, and producer transactions, or wrap it with a higher-level `KafkaLog` that provides those semantics.
- Run one local topology executor per assigned partition.
- Implement assign/revoke lifecycle with `PartitionHandoff`.
- Wire `HttpWebhook<T>` to append to shared log and return HTTP 202 after durable replication.
- Add `event_id` compile-time check and v1 compatibility shim.
- Add `nirdosha-rt dataflow cluster status` CLI.

### Phase 2 — Repartition topics and cross-node shuffle

- Emit keyed repartition records when upstream/downstream `keyed(by = ...)` differ.
- Read assigned repartition partitions into local executor.
- Implement control-topic credit tokens (`CreditGrant`, `CreditReturn`, `CreditRevoke`).

### Phase 3 — Partitioned state snapshots + restore

- Snapshot keyed state per partition on barrier.
- Write snapshots to compacted changelog or object store via `SnapshotBackend`.
- Implement canonical deterministic serializer and Merkle `state_hash`.
- Restore from snapshot + replay on rebalance with retry/fallback.

### Phase 4 — Global barriers and multi-input windows

- Coordinate barrier injection across all source partitions using `__nirdosha_control`.
- Implement combined watermarks.
- Add driver/runtime checks for compatible watermarks on multi-input operators.
- Add delta/incremental snapshot optimization.

### Phase 5 — Self-contained Raft + SWIM mode

- Implement SWIM membership.
- Implement Raft metadata log.
- Provide `RaftLog` `LogProvider` implementation.
- Add node identity and guarantee-bundle fleet attestation.

## 9. Open questions

1. **Exact seccomp-bpf allowlist and non-Linux enforcement:** The mechanism is pinned as seccomp-bpf on Linux, but the precise syscall allowlist/denylist and the enforcement mechanism for macOS/Windows (or non-seccomp Linux builds) need a follow-on security ADR. `OPEN QUESTION: What is the canonical syscall allowlist, and what is the supported non-Linux fallback?`
2. **Control topic scaling:** `__nirdosha_control` is a single-partition topic for Phase 0–3. While control records are small, very large fleets may need a hashed multi-partition control topic; this is deferred. `OPEN QUESTION: At what fleet size does the single-partition control topic become a bottleneck, and what is the multi-partition hashing scheme?`
3. **`KafkaLog` driver layering:** `crates/nirdosha-ingestion-topic-kafka` currently uses `rskafka`, which ADR 0016 notes has no support for consumer groups or transactions. `OPEN QUESTION: Will Phase 1 extend `rskafka`, wrap another client, or implement group/transaction semantics above the partition client?`
4. **Self-contained mode transaction semantics:** When `RaftLog` replaces `KafkaLog`, the exact mapping of `LogTxn` to Raft log entries (per-partition Raft group vs. shared log) is deferred to Phase 5. `OPEN QUESTION: What is the Raft group topology for the metadata and data planes?`
5. **HTTP ingress v1 compatibility shim expansion rules:** The exact set of stable headers and body normalization for the synthesized `event_id` needs to be specified in the macro implementation doc. `OPEN QUESTION: Which request fields are included in the canonical fingerprint?`
6. **Multi-input joins:** Global watermark alignment proof and repartitioning on a common join key are intentionally out of scope for Phase 0–3. `OPEN QUESTION: What is the exact driver check that proves multi-input watermark monotonicity?`
7. **Object-store snapshot backend default:** Whether the self-contained mode uses local RocksDB + shared object store or a Raft-managed chunk store is deferred. `OPEN QUESTION: Which snapshot backend is the Phase 5 default?`
