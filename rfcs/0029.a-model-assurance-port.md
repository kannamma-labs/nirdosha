# RFC 0029.a — Provider-Neutral Model Assurance Port

```
RFC:           0029.a
Title:         Provider-neutral model assurance port
Status:        Proposed — reviewed architecture; nothing in this RFC is
               claimed implemented
Created:       2026-09-26
Extends:       RFC 0029
Motivated by:  RFC 0029 AI-first KYC tabletop, gaps A1–A8
Validation:    RFC 0029.a medical AI tabletop
Expansion:     RFC 0029 cross-domain expansion tabletop
Rerun:         RFC 0029 unified cross-domain conformance rerun
Related:       RFC 0025 (model runtime/provider surface)
               RFC 0026 (metadata and lineage)
               RFC 0017 (guarantee artifacts)
```

## 1. Summary

RFC 0029 requires model identity, status, inference evidence, monitoring, and
policy-controlled suspension before AI output may influence a protected
effect. This amendment defines the missing interface: the **Model Assurance
Port** (MAP).

MAP is a provider-neutral protocol between Nirdosha and an AI model deployment
or its adapter. It standardizes:

- immutable model/deployment identity;
- lifecycle and effective operating state;
- signed status and incident reports;
- per-inference receipts;
- validation, calibration, fairness, adversarial, and drift evidence;
- monitor health and observation completeness;
- promise evaluation and policy-triggered response;
- impact discovery after revocation or compromise;
- conformance requirements for embedded, hosted, generative, and opaque
  models.

The model may report observations and recommend a state. It never unilaterally
decides that its promises are satisfied, promotes itself, or authorizes a
protected domain effect. Nirdosha computes the effective state from admitted
policy and independently sourced evidence.

## 2. Current implementation boundary

The workspace currently has useful but incomplete pieces:

- `model_artifact!` registers model name, format, inputs, outputs, and an alert
  threshold. Its current grammar does not accept a version; registrations use
  an empty version string.
- `nirdosha-scoring-model-onnx` has real `ModelRuntime::load` and
  `Model::score` traits and verifies an artifact SHA-256 before loading.
- RFC 0025 and the RTM example describe model governance, swap approval,
  performance views, and drift views.
- generic service-health records can carry heartbeat-style information.
- lineage represents models as data nodes with artifact versions.

None of these defines a live, model-neutral assurance protocol. In particular,
there is no canonical status envelope, inference receipt, model-state machine,
independent monitor contract, promise evaluator, automatic suspension path,
or conformance suite. Landing this RFC does not change that status.

## 3. Goals and non-goals

### 3.1 Goals

MAP must:

- work with embedded models, local runtimes, remote APIs, sidecars, and
  proprietary providers;
- bind every protected inference to immutable model/deployment identity;
- distinguish model self-report from independent evidence;
- preserve uncertainty, abstention, and out-of-domain results;
- let policy automatically narrow, suspend, or revoke model use;
- bind inference evidence to RFC 0029 decision capabilities;
- make changes, failures, drift, compromise, and blind monitoring visible;
- support exact, semantic, or decision-verification replay honestly;
- avoid forcing sensitive raw data into a centralized assurance plane.

### 3.2 Non-goals

MAP does not:

- prove that a model is universally correct, fair, safe, or truthful;
- turn confidence into calibrated probability without evidence;
- make self-reported health independent evidence;
- require model weights to be disclosed when the provider cannot disclose
  them;
- make an opaque hosted model replayable beyond the evidence it supplies;
- permit an AI model to define or approve its own governing policy;
- replace domain validation, legal review, model-risk governance, red-team
  work, or meaningful human review;
- prescribe one transport or model framework.

## 4. Architecture

```text
                         Policy Administration Point
                      model policy · approval · lifecycle
                                      │
                                      ▼
 Model/provider ──► adapter/sidecar ──► Model Assurance Port
      │                  │              │
      │                  ├─ identity    ├─ schema/signature validation
      │                  ├─ status      ├─ promise evaluation
      │                  ├─ receipts    ├─ state calculation
      │                  └─ incidents   ├─ impact indexing
      │                                 └─ evidence commitments
      │                                         ▲
      ▼                                         │
 Inference gateway                       independent monitors
      │                           probes · labels · drift · fairness · health
      ▼                                         │
 Model output ───────────────► admitted policy decision
                                      │
                                      ▼
                           RFC 0029 decision capability
                                      │
                                      ▼
                              protected effect gateway
```

MAP has four logical roles:

1. **Model Adapter** — translates provider/runtime behavior into canonical MAP
   messages.
2. **Model Assurance Registry** — stores immutable identities, policies,
   lifecycle, and evidence indexes.
3. **Promise Evaluator** — compares current evidence to admitted assurance
   promises and derives findings.
4. **Model State Authority** — computes the effective model state used by
   inference and protected-effect gateways.

These roles may share a process but remain semantically separate.

## 5. Transport and adapter model

MAP defines canonical messages and semantics, not a mandatory wire protocol.
Conformant bindings may include:

- an in-process Rust trait for embedded models;
- local IPC or a sidecar for proprietary runtimes;
- HTTP or gRPC for remote services;
- signed event streams for status, incident, and evidence updates;
- batch evidence imports for independent validation;
- administrative MCP tools for inspection and governance, but not as the sole
  high-volume inference transport.

Every binding must preserve canonical encoding, identity, sequencing,
authentication, replay protection, error semantics, and evidence hashes.
Transport conversion cannot silently omit a required field or weaken a
failure into a default value.

An adapter is part of the TCB for the claims it translates. Its identity,
version, configuration, capabilities, and conformance result are recorded.

## 6. Canonical identifiers

The protocol uses stable identifiers for:

- `model_artifact_id` — immutable model weights/artifact or provider-supplied
  immutable model version;
- `model_family_id` — lineage across related versions;
- `deployment_id` — one configured serving deployment;
- `runtime_id` — runtime/provider implementation and version;
- `adapter_id` — MAP adapter implementation and version;
- `assurance_policy_id` — admitted promise/response policy;
- `validation_set_id` — immutable validation evidence identity;
- `monitor_id` — independent or provider monitor;
- `inference_id` — one inference attempt;
- `status_report_id` — one sequenced status observation;
- `incident_id` — one incident/compromise event;
- `decision_id` — RFC 0029 policy decision influenced by inference;
- `effect_id` — protected effect resulting from that decision.

Identifiers are scoped by an issuing authority and canonical namespace under
RFC 0029 §36.1. Human-readable names are metadata, never identity.

## 7. Model identity manifest

Before a model can enter `Validated`, the registry accepts an immutable,
signed identity manifest containing at least:

- canonical identifiers and authority;
- artifact digest or provider-attested immutable version;
- model family, task, and prohibited uses;
- format and architecture class where available;
- input, feature, preprocessing, tokenizer, output, and explanation schemas;
- training cutoff and declared knowledge cutoff where applicable;
- runtime, adapter, configuration, prompt/template, tool, and dependency
  identities where material;
- operating domain, excluded populations/conditions, and expected input
  quality;
- semantic input contracts for every consequential input (§13.1);
- nondeterminism controls and replay class;
- uncertainty, calibration, abstention, and out-of-domain semantics;
- validation, fairness, adversarial, safety, and privacy evidence references;
- data-provenance and lawful-use declarations;
- required monitors and their independence class;
- decision/effect classes the model is permitted to influence;
- maximum effect-authority tier and prohibited tier transitions (§13.2);
- outcome/harm, label/adjudication, human-system-capacity, and
  deployment-surveillance contracts (§13.3–§13.6);
- retention, locality, confidentiality, and evidence profile;
- expiry, review date, rollback target, and revocation authority;
- signature/attestation chain and content hash.

For opaque hosted models, unavailable fields are explicit, not fabricated.
Admission reduces or rejects claims whose proof requires those fields.

Changing any identity-bearing field creates a new manifest and, where
applicable, a new artifact or deployment identity. A provider alias such as
“latest” is not an immutable version.

## 8. Model lifecycle

The effective state machine is:

```text
Unregistered
    → Registered
    → Validating
    → Validated
    → Shadow
    → Active
    → Degraded
    → Suspended
    → Revoked
    → Retired
```

Additional transitions may return a candidate from `Validating` to
`Registered` or from `Shadow` to `Validated` without activation.

### 8.1 State meanings

| State | Meaning | Protected-effect authority |
| --- | --- | --- |
| `Unregistered` | Unknown identity | None |
| `Registered` | Identity accepted; assurance incomplete | None |
| `Validating` | Validation is running | None |
| `Validated` | Required evidence passed for stated scope | None unless policy explicitly permits offline use |
| `Shadow` | Receives mirrored inputs; outputs cannot authorize effects | None |
| `Active` | May influence declared decisions inside admitted scope | As declared by policy |
| `Degraded` | Some promise or dependency is impaired | Narrowed scope or mandatory escalation only |
| `Suspended` | Temporary prohibition pending investigation/recovery | None for new protected decisions |
| `Revoked` | Authority permanently withdrawn for the version/deployment | None; impact review required |
| `Retired` | Administratively ended without active incident | None |

### 8.2 Transition authority

- A model or adapter may request validation, report degradation, or request
  suspension.
- A model cannot promote itself to `Validated`, `Shadow`, or `Active`.
- Activation, scope change, waiver, rollback, revocation, and retirement are
  meta-policy-governed actions with separation of duty.
- Automatic policy may demote `Active → Degraded/Suspended` without waiting
  for human approval when a fail-closed promise is violated.
- Recovery never automatically restores `Active` unless the assurance policy
  explicitly permits it and all required evidence has become current.

The effective state is derived by Nirdosha. A provider-reported “healthy”
state is only one observation.

## 9. Status report envelope

A status report contains:

- schema version;
- report, model, deployment, runtime, and adapter identities;
- monotonic sequence and previous-report hash;
- observation time, received time, and expiry;
- provider-reported lifecycle recommendation;
- liveness, readiness, dependency, and capacity status;
- request, success, error, timeout, retry, and throttling metrics;
- latency distribution and queue/backlog state;
- abstention, out-of-domain, invalid-input, and low-quality-input rates;
- output distribution and confidence/calibration summaries;
- drift summaries and monitored feature/output schema versions;
- subgroup-assurance summaries where authorized;
- adversarial/tamper/anomaly indicators;
- monitor identities, independence classes, coverage, health, checkpoints,
  loss/sampling, and blind intervals;
- current incidents, restrictions, and recommended scope;
- evidence references and commitments;
- signature or authenticated-channel attestation.

Status freshness is policy-controlled. Sequence rollback, gaps, expiry,
identity mismatch, or signature failure produces an assurance finding and the
declared state response. Missing reports never mean healthy.

## 10. Inference receipt envelope

Every inference that may influence a protected decision produces a receipt
containing:

- schema and inference identity;
- model artifact/family, deployment, runtime, adapter, configuration, and
  prompt/template identities;
- assurance policy and effective model state;
- input schema and normalized input/evidence commitments;
- authoritative fact and derived-feature references;
- output schema and typed outputs;
- uncertainty/calibration interpretation;
- abstention, invalid-input, and out-of-domain flags;
- explanation reference and declared fidelity class;
- random seed/sampling configuration or a declared nondeterminism class;
- start/end times, latency, retries, and provider request identity;
- active status-report and validation-evidence identities;
- policy-relevant limitations or restrictions;
- signature/attestation and receipt hash.

Reusable credentials, raw secrets, and unnecessary personal data are not
stored in receipts. Protected values use governed references or encrypted
evidence according to RFC 0029 §36.11.

No inference receipt is itself permission to perform a domain effect. The PDP
consumes it as an input and binds accepted outputs into an RFC 0029 decision
capability.

## 11. Incident and change envelopes

An incident/change envelope records:

- incident/change identity and type;
- affected model, deployment, runtime, adapter, data, prompt, feature,
  monitor, and provider versions;
- discovered-at, effective-from, and possible-compromise-from times;
- severity and confidence;
- affected task, population, decision, and effect scopes;
- immediate restrictions and recommended state;
- revocation or rollback target;
- impact-query parameters;
- notification and review obligations;
- remediation, revalidation, and closure evidence;
- issuer and signature.

Changes that alter identity-bearing behavior are new versions, not status
updates. Incidents may be reported by the provider, operator, independent
monitor, auditor, domain authority, or Nirdosha itself.

## 12. Evidence sources and independence

Every evidence item declares one independence class:

| Class | Meaning |
| --- | --- |
| `SelfReported` | Produced by the model/provider being evaluated |
| `OperatorObserved` | Produced by the deployment operator |
| `IndependentMonitor` | Produced by a separately controlled monitor |
| `IndependentValidation` | Produced through an approved validation process over governed data |
| `ExternalAuthority` | Produced by a recognized external authority |

Policy specifies the minimum independence required for each promise. A
`SelfReported` item cannot satisfy a promise requiring independent evidence.
Copies of the same provider event through multiple pipelines are one source,
not quorum.

Evidence declares population, sample/window, methodology, uncertainty,
coverage, data version, labels and label delay, subgroup scope, collection
time, expiry, and limitations. Missing or unhealthy monitoring suspends the
corresponding continuous claim under RFC 0029 §36.10.

## 13. Assurance promises

An assurance promise is a typed, versioned predicate over identity, status,
inference receipts, validation evidence, independent observations, and
monitor health. It contains:

- stable promise ID and owner;
- applicable model/deployment/task/population/effect scope;
- required evidence sources and independence;
- evaluation window and freshness;
- predicate and uncertainty treatment;
- violation severity;
- state transition or scope restriction;
- affected-decision query;
- blocking, post-commit, review, notification, and remediation obligations;
- recovery requirements;
- evidence profile.

Standard promise families include:

- identity and artifact integrity;
- schema and feature compatibility;
- availability, latency, capacity, and error rate;
- uncertainty, abstention, and out-of-domain behavior;
- calibration and task performance;
- subgroup assurance;
- drift and operating-domain stability;
- adversarial/fraud resilience;
- explanation availability and fidelity;
- privacy, retention, and locality;
- human-review capacity and independence;
- model/data provenance and lifecycle;
- monitor coverage and health.

The following six contracts are mandatory for any model that can materially
influence a protected effect. They are part of core MAP semantics. A domain
profile specializes their vocabulary, authorities, thresholds, evidence, and
tests; it does not replace them.

### 13.1 Semantic input contract

Each consequential input declares its concept, representation, unit where
applicable, observation or derivation method, authoritative source, event and
collection time, freshness, missingness, quality state, correction/version
semantics, and transformation lineage. Schema compatibility alone is
insufficient: two fields with the same primitive type but different meaning,
unit, method, or time basis are incompatible.

Normalization produces an immutable input commitment used by the inference
receipt. Unknown, stale, contradictory, lossy, or out-of-contract inputs cause
the declared abstention, escalation, degraded-mode, or rejection behavior.
They cannot silently receive a default that changes domain meaning.

### 13.2 Effect authority and autonomy contract

Every model-influenced path declares one maximum authority tier:

```text
Observe < Classify < Prioritize < Recommend < Draft < Approve
        < ExecuteReversible < ExecuteCompensatable < ExecuteIrreversible
```

The ordering describes authority over effects, not model quality. A capability
names the exact tier and effect taxonomy entry; it cannot be reused at a
stronger tier. Promotion requires a newly admitted policy, profile evidence,
approval, and conformance result. Domain profiles may split a tier or forbid
one, but cannot reorder or silently widen it. Physical action, legal status,
fund movement, clinical treatment, and similar consequences remain distinct
effects even if one model output contributes to each.

### 13.3 Outcome, utility, and harm contract

A consequential deployment declares intended benefit, foreseeable harms,
affected parties, operational burden, outcome measures, observation windows,
uncertainty, acceptable bounds, stop/suspend triggers, and remediation. Model
accuracy is supporting evidence, not a substitute for outcome evidence.
Benefits to the operator cannot cancel harms to a subject by aggregation
unless the admitted domain policy explicitly permits and justifies that rule.

### 13.4 Label and adjudication contract

Every label or evaluation endpoint declares its definition, provenance,
adjudicating authority, observation delay, correction and disagreement
process, censoring/missingness, sampling or selection mechanism, and known
intervention/feedback effects. Model-produced labels and downstream decisions
influenced by the model are not independent ground truth. Evidence using
selectively observed outcomes states that limitation and cannot support a
stronger promise without an admitted correction method.

### 13.5 Human-system capacity contract

When safety or legitimacy depends on a human, the deployment declares reviewer
qualification and independence, source-evidence access, queue/load limits,
response bound, escalation capacity, override authority, disagreement path,
quality sampling, and overload behavior. Capacity is monitored like any other
mandatory dependency. Exceeding it narrows or suspends automation rather than
silently converting meaningful review into a click-through step.

### 13.6 Deployment-domain validation and surveillance contract

Validation and effective status are scoped to the exact deployment,
population, environment, input pipeline, workflow, intended use, effect tier,
and time interval. Transfer to a new scope requires admitted equivalence
evidence or local validation. Surveillance covers incidents, drift, outcome
and harm signals, monitor health, affected-decision/effect discovery, recall
or notification, remediation, and revalidation. A globally `Active` label
cannot override a failed or unvalidated local scope.

A promise must state whether it is a runtime guard, atomic prerequisite,
durable-workflow obligation, continuous bounded-impact monitor, or
retrospective control. Monitoring does not become prevention through wording.

## 14. Promise evaluation and effective state

The Promise Evaluator operates over canonical evidence and emits findings:

```text
Satisfied
Violated
Indeterminate
Stale
MonitorUnhealthy
OutsideOperatingDomain
InsufficientEvidence
ConflictingEvidence
```

The Model State Authority combines findings using the admitted assurance
policy. Safe defaults are:

- identity/signature/schema mismatch → `Suspended`;
- artifact or provider compromise → `Revoked` or `Suspended` as declared;
- stale mandatory evidence → `Degraded` or `Suspended`;
- out-of-domain or low-quality input → per-inference abstention, never silent
  extrapolation;
- calibration/fairness/adversarial violation → affected-scope narrowing or
  suspension plus impact review;
- unhealthy monitor → suspend the affected continuous claim and apply its
  declared state response;
- conflicting mandatory evidence → `Indeterminate` and escalation;
- unavailable optional evidence → no upgrade beyond the remaining evidence.

The effective state is monotonically no stronger than the weakest mandatory
promise for the requested decision scope. A healthy global status cannot
override a failed subgroup, geography, document type, product, or task scope.

## 15. Binding to RFC 0029 decisions and effects

When a model output influences a protected decision:

1. the inference gateway verifies model/deployment/adapter identity;
2. it verifies the effective state permits that task, population, and effect;
3. it validates semantic input contracts and records the inference receipt;
4. the PDP evaluates domain policy using the inference as an explicitly typed
   inference, not an authoritative fact;
5. uncertainty, abstention, OOD, and limitations participate in the decision;
6. the PDP verifies the requested effect-authority tier does not exceed the
   admitted maximum, then binds the receipt and current promise evidence into
   the RFC 0029 decision capability;
7. the protected-effect gateway consumes that capability;
8. effect/evidence finality follows RFC 0029 §23/§36.4;
9. lineage links input facts → inference → decision → effect;
10. outcome, label, human-capacity, and surveillance events update the
    applicable promises;
11. later incidents can query every affected decision and effect.

A decision capability is invalid if the model was not permitted for that
effect scope, required assurance evidence expired before effect commit, the
receipt does not match the normalized inputs, or an invalidating incident was
effective before commit.

## 16. Human review

MAP supports but does not manufacture meaningful human judgment. A
human-review contract declares:

- qualification and role;
- independence from model ownership and prior decisions;
- workload/capacity and minimum evidence access;
- prohibited self-review and model-self-certification paths;
- required affirmative reason or evidence assessment;
- override authority and limits;
- review deadline and escalation;
- disagreement and second-review rules;
- quality sampling and rubber-stamp detection;
- reviewer decision evidence.

A human click is not accepted as independent judgment merely because it came
from a human identity. Models may summarize evidence, but the review UI must
distinguish source evidence from generated interpretation.

## 17. Explanation, correction, and appeal

Every protected decision influenced by a model declares:

- explanation audience and disclosure constraints;
- stable reason codes tied to the actual policy and model path;
- model explanation fidelity class;
- notice requirements;
- correction and appeal entry points;
- review authority and separation of duty;
- deadlines and interim effects;
- affected-decision and affected-effect discovery;
- re-evaluation and remediation behavior.

Generated natural-language explanations are presentation, not evidence of
causal fidelity. Where faithful model explanation is unavailable, the system
must say so and provide the policy facts/reasons it can establish.

## 18. Fairness and subgroup assurance

When applicable and legally permitted, the assurance policy declares:

- protected/relevant cohorts and authority for cohort attributes;
- task-specific outcome and error metrics;
- sample-size and uncertainty requirements;
- evaluation windows and label delays;
- disparity limits or review thresholds;
- intersectional and sparse-cohort behavior;
- response, suspension, threshold-change, and remediation rules;
- privacy and purpose restrictions on sensitive attributes.

Global average performance cannot satisfy a subgroup promise. A subgroup
finding narrows only the affected scope when the policy and gateway can
reliably identify it; otherwise the response applies to the wider model scope.

MAP does not define what fairness standard is legally or ethically correct.
The domain authority defines the standard and Nirdosha enforces the admitted
assurance contract.

## 19. Adversarial assurance

The model threat model may include:

- evasion and presentation attacks;
- deepfakes and synthetic identities;
- document tampering;
- prompt, retrieval, tool, and data injection;
- model/data poisoning;
- extraction, inversion, and membership inference;
- replay and coordinated multi-account attacks;
- compromised provider/runtime/adapter;
- denial of service and resource exhaustion.

The assurance contract declares required layered controls, red-team corpus,
test recency, detection, residual risk, fail behavior, incident response, and
independence. One model's self-reported fraud or liveness score is not proof
that the input is authentic.

## 20. Drift and continuous assurance

Continuous model assurance covers, where applicable:

- input and feature drift;
- schema and preprocessing drift;
- output and confidence drift;
- calibration decay;
- subgroup degradation;
- concept/fraud adaptation;
- abstention and OOD changes;
- label delay and label-quality changes;
- feedback loops and selective-label bias;
- provider/runtime/configuration changes;
- monitor coverage and health.

Every monitor follows RFC 0029 §36.10. Drift statistics without a healthy,
complete observation path cannot sustain an assurance promise. A threshold,
prompt, feature, preprocessing, provider, runtime, or model change is governed
as configuration or identity change, not hidden inside a health report.

## 21. Confidentiality and data lifecycle

MAP messages and evidence are protected resources under RFC 0029 §36.11.
Policies declare:

- which raw values may leave the inference gateway;
- field-level classification and purpose;
- permitted transformations and feature derivation;
- locality and confidential-computing requirements;
- retention, deletion, legal hold, and data-subject rights;
- provider training/retention prohibition or authority;
- prompt, trace, telemetry, and support-access controls;
- training/validation/calibration/monitoring data provenance and lawful use;
- model inversion and leakage controls.

MAP supports hashed commitments and governed references so centralized model
status does not require centralized raw KYC, health, financial, or other
sensitive data.

## 22. Failure and outage behavior

The assurance policy declares behavior for:

- provider unavailable or timing out;
- adapter unavailable;
- status stale or missing;
- receipt missing or invalid;
- monitor unhealthy or blind;
- evidence store unavailable;
- identity/configuration mismatch;
- inference outside operating domain;
- conflicting validation evidence;
- revocation or incident publication;
- state registry unavailable.

Responses use RFC 0029 safety postures. `FailOperationalBounded` or
`HumanControlledEmergency` must be explicitly admitted and cannot silently
continue autonomous AI decisions without current assurance evidence. Local
cached state is bounded by its validity and revocation assumptions.

## 23. Impact discovery and remediation

The registry maintains indexes from model/deployment/status/validation/
monitor/report versions to inference receipts, decisions, and effects.

On incident or revocation, the system can identify:

- decisions still awaiting effects, whose capabilities are invalidated;
- in-flight workflows requiring revalidation;
- completed reversible or compensatable effects;
- irreversible effects requiring notification or specialist review;
- affected subjects, resources, products, jurisdictions, populations, and
  time windows;
- evidence and authorities used at the time.

Remediation may include suspension, rollback, re-score, re-review,
restriction, correction, notification, compensation, or no action with an
approved reason. Re-scoring with a new model does not erase the historical
decision.

## 24. Conformance profiles

### 24.1 Embedded deterministic model

Requires artifact digest, runtime/config identity, schemas, deterministic or
bounded-nondeterministic receipt, local status, independent validation, and
gateway binding.

### 24.2 Hosted opaque scoring model

Requires provider/deployment attestation, stable version contract, adapter
identity, schemas, receipts, external health/status, validation evidence, and
declared replay limitation. If provider identity can change behind an alias,
the deployment cannot be `Active` for protected decisions requiring immutable
identity.

### 24.3 Generative model

Also requires prompt/template, tool/retrieval, sampling, output-validation,
injection, nondeterminism, and explanation-fidelity declarations. Free-form
text is not directly consumed as a protected decision; a typed validator must
accept or reject it.

### 24.4 Ensemble or chained models

Every component and composition function has an identity and receipt.
Authority, disagreement, fallback, and partial-failure behavior are explicit.
Multiple models from the same provider/data lineage are not automatically
independent evidence.

### 24.5 Human-plus-model system

Adds the meaningful-review contract in §16 and binds both inference and human
decision evidence to the final capability.

### 24.6 Medical clinical decision support

The medical profile is specified and failure-tested in the companion
[medical AI tabletop](./evidence/0029/tabletops/medical-ai.md). It adds intended-use
and regulatory-status binding, clinical measurement semantics, autonomy/effect
risk tiers, clinical benefit/harm endpoints, label/adjudication and
intervention-feedback semantics, workflow capacity/human factors, local
validation/transportability, and post-market safety/recall. This profile is
proposed and unimplemented. M2–M8 specialize §13.1–§13.6; M1 additionally
binds intended use and regulatory status. The unified rerun records the
result after this semantic merge.

### 24.7 AI-first KYC

Specializes semantic inputs for identity/document/screening evidence,
authority tiers for onboarding and restrictions, customer/adverse-decision
harm, delayed and disputed labels, qualified investigator capacity, and
jurisdiction/product-specific validation and surveillance.

### 24.8 Manufacturing AI

Specializes sensor and asset semantics, separates recommendations and
reversible holds from physical actuation, declares safety/product harms,
quality/failure label adjudication, operator/engineer capacity, and
machine/line/configuration-specific validation. It cannot substitute for a
safety-rated controller or physical safety case.

### 24.9 Insurance AI

Specializes contract/evidence inputs, authority over claim and customer
effects, policyholder/claimant harms, delayed or contested claim/fraud labels,
adjuster/investigator capacity, and product/jurisdiction/catastrophe-specific
validation and surveillance.

The findings and profile boundaries are recorded in the
[cross-domain expansion tabletop](./evidence/0029/tabletops/cross-domain-expansion.md).
Their common rerun is recorded in the
[unified conformance rerun](./evidence/0029/tabletops/unified-conformance-rerun.md).

## 25. Administrative interface

The administrative surface supports, subject to meta-policy:

- register manifest;
- submit validation evidence;
- request validation;
- activate shadow mode;
- request/promote activation through approval;
- narrow scope;
- suspend, revoke, retire, and roll back;
- ingest status/incident reports;
- query effective state and promise findings;
- query impacted decisions/effects;
- acknowledge/remediate incidents;
- export governed evidence and assurance reports.

No “set status = healthy” operation exists. Administrators submit evidence or
perform governed lifecycle actions; the effective state remains derived.

## 26. Security requirements

MAP requires:

- authenticated workload/provider/adapter identity;
- message integrity, sequence, freshness, and replay protection;
- least-privilege submit/query/admin scopes;
- separation of model owner, validator, activator, and incident closer where
  policy requires it;
- protected keys and rotation;
- append-only or equivalently tamper-evident lifecycle/evidence records;
- rate, size, and fan-out limits;
- schema and decompression safety;
- no execution of provider-supplied content as instructions;
- bounded status/evidence parsing;
- audit of reads as well as writes for sensitive evidence;
- explicit trust and compromise recovery for provider and adapter identities.

## 27. Formal and conformance prerequisites

## 31. Final principle

MAP does not ask a model whether it kept its promises and accept “yes.” It
binds the model's immutable identity and per-inference receipts to admitted
policy, combines self-report with evidence of declared independence, derives
an effective lifecycle state, and prevents or narrows protected effects when
required assurance is absent.

The resulting honest claim is:

> This model deployment was permitted to influence these decision classes,
> under this assurance policy and operating domain, using these recorded
> versions and evidence. Required promises were satisfied at the declared
> verification times; uncertainty and exclusions remained explicit; and
> violations triggered the declared state and remediation behavior.

It is not:

> The model is correct because it reported itself healthy.
## Model Influence Overlay

```
Parent:        RFC 0029 and RFC 0029.a
Status:        Candidate Phase 0 contract; not implemented or certified
Created:       2026-09-27
```

## 1. Purpose

AI is not a binary property of a domain, application, workflow, or deployment.
A manufacturing process, insurance service, hospital, or bank may contain
decisions with no model influence, advisory model influence, human-plus-model
authority, and bounded automated effects at the same time.

This overlay binds model participation to a specific RFC 0029 decision/effect
class. The underlying domain profile remains authoritative for resources,
effects, finality, safety, applicability, and domain correctness. RFC 0029.a
adds model identity, receipt, assurance, monitoring, and impact requirements
only where model influence exists.

## 2. Normative rule

Every protected decision/effect class declares exactly one model-influence
binding. `None` means no model output, model-derived fact, model-selected
presentation, or model-controlled routing materially influences the decision.
All other levels activate the applicable RFC 0029.a requirements.

A final human click does not change a model-influenced decision to `None`.
The binding follows material influence through the decision lineage.

## 3. Influence and authority levels

The ordered levels are:

```text
None
  < Observe
  < Classify
  < Prioritize
  < Recommend
  < Draft
  < Approve
  < ExecuteReversible
  < ExecuteCompensatable
  < ExecuteIrreversible
```

The order describes increasing effect authority, not intelligence, quality,
autonomy, risk, or assurance. A domain profile may subdivide a level, prohibit
it, or require independent authority. It may never silently widen it.

| Level | Maximum generic meaning |
| --- | --- |
| `None` | No material model influence |
| `Observe` | Produce a measurement/observation without classifying the domain outcome |
| `Classify` | Assign a label or category that remains an inference |
| `Prioritize` | Change ordering, urgency or attention allocation |
| `Recommend` | Propose an action without creating an authorized action artifact |
| `Draft` | Create a draft action/artifact requiring admitted review and approval |
| `Approve` | Supply an approval recognized by the domain workflow within an explicitly bounded class |
| `ExecuteReversible` | Perform an effect that the domain profile proves reversible |
| `ExecuteCompensatable` | Perform an effect whose consequences require a later compensating effect |
| `ExecuteIrreversible` | Perform an effect that cannot be undone; unsupported unless an explicit high-risk profile admits it |

## 4. Candidate binding shape

This is a semantic shape, not a frozen serialization:

```yaml
model_influence_binding:
  decision_class: manufacturing.product_quarantine
  protected_effect: product.quarantine
  level: ExecuteReversible

  sources:
    - model_deployment_id: model-deployment:vision-line-4:v12
      inference_receipt_required: true
      material_inputs:
        - image.capture
        - product.configuration
      output_semantics: defect_classification

  lineage:
    combination: deterministic_rule_after_model
    human_review: none
    downstream_rules:
      - rule: quarantine-if-defect-probability-over-approved-threshold

  authority_boundary:
    maximum_level: ExecuteReversible
    prohibited_effects:
      - product.release
      - machine.restart

  required_promises:
    - semantic_input_contract
    - effect_authority_contract
    - outcome_harm_contract
    - label_adjudication_contract
    - deployment_validation_surveillance

  failure_behavior:
    invalid_or_missing_receipt: Deny
    model_state_degraded: Defer
    model_state_suspended: Deny
    monitor_health_unknown: SuspendAffectedAuthority
```

## 5. Material influence

The normative graph, reachability, review-mode and diagnostic semantics are
defined in
[RFC 0029 — Model Influence and Human Review Semantics](./evidence/0029/influence-review/original-semantics.md).
This section is the explanatory summary; where wording differs, that document
controls the candidate Phase 0 interpretation.

Model influence is material when it can change any of:

- candidate generation or eligibility;
- classification, risk, priority or queue position;
- information shown or hidden from a reviewer;
- default, framing, explanation or proposed reason;
- required review path or approval threshold;
- decision outcome or obligation;
- effect parameters, target, timing or gateway;
- whether an effect is attempted at all.

Purely operational model use that cannot affect a protected decision or
effect may remain outside that decision's binding, but the exclusion and its
non-influence argument must be reviewable. A model-generated feature consumed
by a deterministic rule is still model influence.

## 6. Human-plus-model decisions

Human review is represented independently from the influence level:

```yaml
human_review:
  required: true
  authority: role:licensed-adjuster
  independence: independent_decision
  required_information:
    - source evidence
    - model limitations
    - uncertainty_and_abstention
    - policy-grounded reasons
  capacity_contract: insurance.catastrophe-review-capacity
  disagreement_allowed: true
  rubber_stamp_monitor: required
```

Review does not erase model lineage. The profile declares whether the human
independently decides, approves a bounded draft, or merely acknowledges an
automated decision. Only the first two can satisfy a human-authority
requirement, and only when capacity, information, independence, timing and
override evidence are current.

## 7. Mixed workflows

A workflow may use different bindings per transition:

| Manufacturing decision/effect | Binding |
| --- | --- |
| Read attested vibration sensor | `None` |
| Detect anomaly | `Classify` |
| Rank maintenance queue | `Prioritize` |
| Propose maintenance window | `Recommend` |
| Draft work order | `Draft` |
| Approve shutdown | `None` or model-influenced human approval as actually configured |
| Place bounded product quarantine | `ExecuteReversible` |
| Release safety-critical product | Model authority prohibited by initial profile |
| Restart hazardous cell | Model authority prohibited by initial profile |

| Insurance decision/effect | Binding |
| --- | --- |
| Extract fields from documents | `Classify` |
| Route claim | `Prioritize` |
| Estimate damage | `Recommend` |
| Draft adjustment | `Draft` |
| Approve admitted low-value claim | `Approve` |
| Deny/cancel/non-renew | Model authority prohibited by initial profile |
| Issue payment to authoritative payee | Model authority prohibited by initial profile |

## 8. Gradual adoption and change

Changing a binding is a governed policy change, not a deployment label. A
decision may progress independently:

```text
None → Observe → Classify → Recommend → Draft
```

Higher authority is not an automatic maturity progression. `Approve` or an
execution level requires the domain profile, assurance promises, conformance
tests, effect gateway, evidence, safety posture and meta-policy to admit that
exact class.

Every change records old/new binding, model/deployment identities, affected
scope, new promises, validation evidence, approver, effective interval,
rollback condition and affected-decision discovery plan. Shadow evaluation
does not alter the active binding.

## 9. Composition with the domain profile

The effective requirements for a decision are the conjunction of:

```text
RFC 0029 universal requirements
  + domain profile requirements
  + model-influence overlay requirements
  + deployment-specific admitted policy
```

The overlay cannot:

- redefine a resource or effect identity;
- turn an inference into an authoritative domain fact;
- change external finality or reversibility;
- exceed a safety, legal, professional or organizational authority floor;
- replace a required independent authority with provider self-report;
- weaken domain obligations, explanations, appeal or evidence;
- convert monitoring or accepted risk into prevention.

## 10. Assurance activation

Any non-`None` binding requires immutable model/deployment/runtime/adapter
identity and an inference receipt or a profile-defined equivalent for bounded
embedded deterministic models. Additional promises activate according to the
decision's inputs, authority and consequences:

| Condition | Required assurance |
| --- | --- |
| Consequential typed inputs | Semantic input compatibility |
| Protected effect influence | Effect-authority and capability binding |
| Consequential outcome | Outcome, utility and harm contract |
| Observed performance claim | Label/adjudication provenance |
| Required human review | Human-system capacity and independence |
| Evidence transferred to a deployment | Deployment-domain equivalence/validation |
| Continuous authority | Monitor health, drift and surveillance |
| Adverse or contestable outcome | Faithful explanation, correction and appeal |
| Revocation/compromise | Impact discovery and remediation |

## 11. Admission rules

Admission rejects or returns `Indeterminate` when:

- a protected decision omits its binding;
- `None` is declared but model lineage materially influences the decision;
- the requested level exceeds the domain profile's maximum;
- a downstream effect is stronger than the bound authority;
- a required receipt, promise or effective-state fact is missing/stale;
- human review lacks required independence, information, capacity or time;
- the model output is promoted to an authoritative fact without an admitted
  adjudication process;
- the deployment scope lacks validation/equivalence;
- changed model input, identity, prompt, configuration or scope reuses an old
  capability;
- a suspended/degraded model retains authority forbidden by policy.

## 12. Conformance matrix

Every domain profile using the overlay supplies cases for:

- `None` with proof of no material model influence;
- each admitted influence level and its next prohibited level;
- hidden model-derived features and deterministic downstream rules;
- human agreement, disagreement, override and rubber-stamping;
- abstention, OOD, uncertainty and invalid input;
- model/provider/configuration/prompt change;
- stale, missing, replayed, duplicated and mismatched receipts;
- monitor blindness and degraded/suspended effective state;
- profile/deployment mismatch;
- attempted inference-to-authoritative-fact promotion;
- attempted authority escalation to a stronger downstream effect;
- rollback and affected-decision discovery.

## 13. Phase 0 acceptance

This overlay is ready to freeze only when the manufacturing, insurance, KYC
and medical/healthcare profiles encode mixed workflows without parallel
“AI-domain” schemas; equivalent model influence produces the same core/MAP
requirements across domains; and domain-specific vocabulary remains in the
profiles. Executable conformance remains required before any binding is
advertised as supported.

## 1. Precedence and scope

This document replaces the candidate semantics for edge typing, influence
folding, authority transition, observational separation, review-mode
evaluation, capability authority, invalidation and golden fixtures. Where it
conflicts with the original influence/review document, this revision controls.

It deliberately distinguishes three values:

1. **provenance influence** — whether a model contributed anywhere upstream;
2. **model authority level** — the strongest action the model itself supplied
   before an independent authority transition; and
3. **final capability authority** — the effect authority supplied by the
   complete domain authority chain.

These values are never collapsed.

## 2. Canonical graph model

The lineage graph is a finite DAG with canonical node and edge records. Node
IDs are content-independent stable instance IDs; equality for classification
uses kind and bound semantic identity, not display text.

### 2.1 Node kinds

```text
Fact(authority_class, type_id, version)
ModelInvocation(model_deployment_id, receipt_id)
Transform(transform_id, version)
Rule(rule_id, bundle_hash)
CandidateSet(candidate_type)
Presentation(surface_id, version)
Review(review_contract_id, mode)
AuthorityAssertion(assertion_kind, authority_id, contract_id)
Decision(decision_class)
Obligation(obligation_type)
Capability(effect_class)
Effect(effect_id, reversibility_class)
Evidence(evidence_type)
```

`AuthorityAssertion` is the universal authority-transition primitive added by
this revision. It does not delete upstream provenance.

### 2.2 Edge algebra

Every edge has exactly one kind. The table is closed; unknown kinds reject
admission.

| Edge | Allowed source → target | Semantic role | Model-level contribution |
| --- | --- | --- | --- |
| `DataFlow` | Fact/ModelInvocation/Transform → Transform/Rule/CandidateSet/Presentation/Review/AuthorityAssertion/Decision | Structural value dependency | none |
| `RuleFlow` | Rule → CandidateSet/Presentation/Review/AuthorityAssertion/Decision/Obligation/Capability | Structural rule-result dependency | none |
| `CandidateGenerate` | ModelInvocation/Transform/Rule → CandidateSet | Determines available candidate | `Classify` |
| `CandidateSuppress` | ModelInvocation/Transform/Rule → CandidateSet | Removes candidate/option/evidence | `Classify` |
| `Eligibility` | ModelInvocation/Transform/Rule/CandidateSet → Decision | Determines eligibility | `Classify` |
| `Rank` | ModelInvocation/Transform/Rule → CandidateSet/Presentation | Changes order/priority | `Prioritize` |
| `Attention` | CandidateSet/Presentation → Review/Decision | Changes what/when a reviewer sees | `Prioritize` if model-reachable |
| `Default` | ModelInvocation/Transform/Rule → Presentation/Review/Decision | Supplies preselected outcome/action | `Draft` |
| `Recommend` | ModelInvocation/Transform/Rule → Presentation/Review/Decision | Suggests action without actionable artifact | `Recommend` |
| `DraftArtifact` | ModelInvocation/Transform/Rule → Review/AuthorityAssertion/Decision | Creates non-final actionable draft | `Draft` |
| `DraftReason` | ModelInvocation/Transform/Rule → Presentation/Review/AuthorityAssertion | Creates proposed reason/explanation | `Draft` |
| `ModelApproval` | ModelInvocation/Transform/Rule → Decision/Capability | Model output counts as approval | `Approve` |
| `ModelTrigger` | ModelInvocation/Transform/Rule/Decision → Effect | Model directly causes effect attempt | effect reversibility level |
| `HumanInput` | Presentation/Review → AuthorityAssertion | Evidence of declared human protocol | none; retains upstream provenance |
| `AssertFact` | AuthorityAssertion → Fact | Creates authority-qualified asserted fact | authority transition |
| `AssertDecision` | AuthorityAssertion → Decision | Supplies independent/bounded domain decision | authority transition |
| `Authorize` | Decision/AuthorityAssertion → Capability | Supplies final domain authorization | none for model level unless source is model-reachable without authority transition |
| `Require` | Decision/Rule → Obligation | Declares obligation | none |
| `Satisfy` | Fact/Review/Evidence → Obligation | Supplies obligation evidence | none |
| `Issue` | Capability → Effect | Consumes capability for effect | none |
| `Record` | any → Evidence | Post/parallel evidence relation | never influences recorded target |
| `ObserveOnly` | ModelInvocation/Transform → Evidence | Isolated shadow observation | none; requires §6 certificate |

### 2.3 Exclusivity and overlap rules

- `DataFlow` and `RuleFlow` are structural and never encode a semantic action.
- A semantic relationship uses its specific edge instead of `DataFlow`.
- `DraftReason` is only reason content; `DraftArtifact` is an actionable domain
  artifact. If both occur, emit both edges.
- `ModelApproval` is model-supplied approval. `Authorize` is final domain
  authorization and does not imply who influenced it.
- `ModelTrigger` exists only where a model-reachable path causes an effect
  without an intervening independent authority assertion for that effect.
- `Record` and `ObserveOnly` cannot target Decision, Capability, Obligation or
  Effect.
- Edges violating endpoint constraints reject with `InvalidLineageEdge`.

### 2.4 Consequential-path completeness

For every active path from `ModelInvocation` to `Review`,
`AuthorityAssertion`, `Decision`, `Obligation`, `Capability`, or `Effect`, at
least one edge before that protected node must be a semantic contribution edge
from §2.2. A path made only of `DataFlow`/`RuleFlow` is invalid and produces
`SemanticEdgeMissing` plus `InfluenceUnknown`.

The only exception is a path that terminates exclusively in Evidence through
`ObserveOnly` with a valid §6 certificate. Structural edges can transport a
value between semantic operations; they cannot classify consequential model
use as mere observation.

## 3. Canonical normalization

Before classification, normalize the graph:

1. validate node/edge endpoint constraints and acyclicity;
2. retain every semantic edge;
3. contract any chain of only `DataFlow`/`RuleFlow` edges through
   `Transform`/`Rule` nodes into structural reachability;
4. do not contract `CandidateSet`, `Presentation`, `Review`,
   `AuthorityAssertion`, Decision, Capability or Effect nodes;
5. deduplicate identical semantic edges after contraction;
6. sort nodes/edges by canonical kind and stable ID for encoding only.

Neutral decomposition equivalence is defined as equality of normalized
semantic edges, authority assertions and protected targets. Inserting or
removing structurally equivalent Transform/Rule nodes cannot change the fold.

## 4. Representation-invariant influence fold

For each model invocation `m` and protected target `t`, propagate states:

```text
State = {
  provenance_reachable: bool,
  model_level: InfluenceLevel,
  model_authority_active: bool
}
```

Initial state at `m`:

```text
{ true, Observe, true }
```

Fold rules:

1. structural edges preserve state;
2. a semantic model-contribution edge raises `model_level` by `max` only when
   `model_authority_active` is true;
3. `HumanInput` preserves provenance and level;
4. a valid `AuthorityAssertion` sets `model_authority_active = false` for the
   assertion's outgoing `AssertFact`, `AssertDecision`, and `Authorize` paths;
5. downstream domain authorization does not raise the upstream model level;
6. another ModelInvocation joining downstream starts a new active model state;
7. merged paths retain provenance, take maximum model level, and keep model
   authority active if any incoming path remains active;
8. `ModelTrigger` maps to ExecuteReversible/Compensatable/Irreversible using
   the target Effect's declared reversibility;
9. a domain prohibition rejects even if the fold is otherwise defined.
10. a consequential structural-only path fails §2.4 before folding and cannot
    produce `Observe`.

The target result contains:

```text
provenance_influenced: bool
computed_model_level: InfluenceLevel | None | Unknown
model_authorized_target: bool
final_authority_chain: [AuthorityRef]
final_capability_authority: EffectAuthority
```

`computed_model_level` and `final_capability_authority` are independent.

## 5. Authority assertion and adjudication

An `AuthorityAssertion` record is:

```yaml
assertion_id: stable-id
kind: IndependentDecision | BoundedApproval | FactAdjudication
authority: authority-id-and-version
contract: review-or-adjudication-contract-id-and-version
inputs: [node-id-and-version]
upstream_model_influence:
  provenance: true
  computed_level: Recommend
output:
  kind: Fact | Decision
  type: domain-type-id
  value_commitment: hash
effective_at: timestamp
failure_behavior: Deny | Indeterminate | Escalate
evidence: evidence-id
```

The assertion changes the authority of its output, not history:

- upstream model provenance remains queryable and bound to evidence;
- the assertion records the influence level on the adjudicator;
- the new fact/decision has the named asserting authority;
- downstream model influence does not automatically continue as active model
  authority beyond the assertion;
- a later policy may still treat the upstream influence as relevant and bind
  it into its evidence/capability;
- `Acknowledgement` cannot create an authority assertion;
- self-certification or missing independence prevents the transition.

### 5.1 Assertion coverage and dominance

Every assertion declares `covered_input_origins`, `covered_model_paths`, and
`covered_targets`. Coverage binds normalized semantic origins, not removable
Transform/Rule node IDs. A semantic origin is the nearest non-contractible
upstream node plus its version/commitment; structural nodes normalize to the
origin(s) that feed them. `covered_model_paths` and `covered_targets` likewise
use normalized stable identities. For target `t`, assertion `a` terminates
active model authority only when:

1. `t` is in `covered_targets`;
2. every model-active path from each observed ModelInvocation to `t` passes
   through `a` and exits through `AssertFact`, `AssertDecision`, or
   `Authorize`;
3. every normalized model-reachable input origin to `a` is in
   `covered_input_origins`;
4. the assertion's review/adjudication contract passes; and
5. no unmodeled or structural-only model path reaches `t`.

This is dominance over the normalized graph. A bypassing classified path
keeps `model_authorized_target = true`; an unclassified bypass produces
`InfluenceUnknown`. A contract requiring an independent final decision fails
with `AuthorityAssertionCoverageIncomplete`.

Equivalent human-reviewed processes must route every covered model
contribution through the assertion. A parallel model-to-decision authorization
edge means the model remains an authorizing source and cannot be described as
independent review.

Normalization rewrites assertion coverage before equivalence comparison:

```text
normalize_coverage(ids) = sorted unique union of semantic_origins(id)
```

Thus an assertion covering `ModelInvocation → Transform → Rule → Review`
binds the same origins as one covering `ModelInvocation → Review` when the
Transform/Rule chain contains only structural edges.

## 6. Closed `ObserveOnly` non-interference certificate

`ObserveOnly` is accepted only with a versioned certificate:

```yaml
boundary:
  components: [...]
  protected_targets: [...]
dependency_graph_hash: sha256:...
model_sink: component-id
allowed_channels:
  - source: decision-copy-tap
    target: isolated-shadow-sink
    direction: one-way
forbidden_return_classes:
  - data
  - control
  - configuration
  - scheduling_priority
  - shared_mutable_state
  - credential_or_capability
enforcement:
  mechanism_id: sandbox-or-network-policy-id
  version: ...
  attestation: ...
shared_resources:
  - resource-id
  - declared_noninterference_rule
valid_from: ...
valid_until: ...
invalidation:
  - topology-change
  - policy-change
  - credential-change
  - shared-resource-change
unmodeled_channel_behavior: Indeterminate
```

Admission deterministically accepts only when:

1. every boundary component and dependency is in the hashed graph;
2. graph reachability contains no path from model sink to a protected target
   through data, control, configuration, scheduling, shared mutable state or
   credentials/capabilities;
3. each allowed channel is one-way and enforced by an identified attested
   mechanism inside the declared TCB;
4. every shared resource has a profile-approved non-interference rule;
5. the certificate is current and unrevoked;
6. unmodeled channels are absent by closed-world attestation or yield
   `Indeterminate`.

Resource-exhaustion/timing channels are non-interfering only if the profile
declares and the enforcement attests isolation/bounds sufficient for the
protected decision class. Otherwise `ObserveOnly` is rejected.

## 7. Review contracts are declared, not inferred

Review mode is a field of a versioned contract. Validation answers only
`Pass`, `Fail(finding)`, or `Indeterminate`; it never infers the “best” mode.
Contracts may reuse predicates, but satisfying another mode does not change
the declared mode.

Every predicate is referenced as:

```text
PredicateRef {
  id,
  version,
  authority,
  evaluated_at,
  validity,
  failure_behavior: Deny | Indeterminate | Escalate
}
```

Each reference resolves to one immutable definition and evaluation:

```text
PredicateDefinition {
  id, version,
  kind: Qualification | Authority | Independence | EvidenceAvailable |
        EvidenceAccessed | LimitationVisible | ExplicitAction |
        ReasonBound | OverrideAvailable | EscalationAvailable |
        CapacityHealthy | IndependentOutcomeChoice | SamplingAssigned |
        ProfileExtension(type_id),
  expression: CanonicalBoundedPredicate,
  input_schema,
  result_type: Bool,
  authority,
}

PredicateEvaluation {
  definition_id, definition_version, evaluator_authority,
  inputs: [typed-value-or-protected-reference-and-version],
  input_commitment,
  result: True | False | Unknown,
  evidence_commitment,
  evaluated_at, valid_until, revoked,
}
```

Admission verifies definition identity, bounded expression, input schema,
authority and failure behavior. Runtime verifies exact inputs, evaluator,
result/evidence commitments, validity and revocation. An opaque external
predicate supplies an authority-signed result and cannot support incompatible
static claims.

Review contracts are conjunctions. Result is independent of evaluation order:

1. any current `False` yields `Fail` with every false finding;
2. otherwise missing, stale, revoked or `Unknown` evaluations apply declared
   failure behavior with precedence `Deny > Indeterminate > Escalate`;
3. otherwise all predicates are `True` and the declared mode passes.

`Deny` yields `Fail(ReviewPredicateFailedClosed)`, `Indeterminate` yields an
indeterminate review, and `Escalate` yields
`Fail(ReviewEscalationRequired)` with the named target.

## 8. Influence versus final capability authority

A capability records both:

```yaml
model_influence:
  provenance: true
  computed_level: Recommend
  model_authorized_target: false
final_authority:
  effect: settlement.approve
  authority_chain:
    - role: qualified-adjuster
    - assertion: independent-decision-123
  maximum_effect: settlement.approve
```

Rules:

- the model cannot authorize above `computed_level` or the domain maximum;
- an independent valid authority assertion may authorize a stronger effect;
- the stronger final effect does not retroactively raise or erase the model
  influence level;
- the capability binds both values and the assertion/review evidence;
- a BoundedApproval cannot exceed its declared effect boundary;
- an IndependentDecision cannot exceed the reviewer's domain authority;
- self-certification never creates independent authority.

## 9. Dependency-specific invalidation

Every bound dependency declares:

```text
DependencyBinding {
  dependency_id,
  version_or_validity,
  trigger,
  before_reservation: Deny | Reevaluate | Suspend,
  after_reservation_before_commit: Abort | ReevaluateAtomically,
  after_local_commit: Reconcile | SuspendDownstream | Compensate | ImpactReview,
  after_external_unknown: Reconcile | SuspendDownstream | ImpactReview,
  after_finality: ImpactReview | Notify | GovernedReopen,
}
```

Reservation/consumption and the protected local effect share the gateway's
declared atomic boundary where `Atomic` is claimed. An invalidation observed
before commit follows the bound action inside that boundary. Retrospective
revocation never rewrites history; it triggers affected-decision discovery and
the post-finality action. External possible acceptance enters
`UnknownOutcome` and its reconciliation action.
