# RFC 0021.a: Workflow definitions as authoring graph data

> **Status: substantially implemented, 2026-09-18** (corrected from a
> stale "proposed, not implemented" header). `Workflow`/`WorkflowState`/
> `WorkflowTransition`/`ApprovalPolicy` are real, schema-registry-
> validated node kinds (`crates/nirdosha-graph/src/schema.rs`), and all
> five of this RFC's own derived edges — `CONTAINS`, `TRANSITIONS_TO`,
> `ON_ENTRY`, `ON_EXIT`, `REQUIRES_APPROVAL` — are computed mechanically
> in `store/mutations.rs::derive_edges` (confirmed 2026-09-18; an
> earlier pass had flagged these as unconfirmed/likely-missing without
> having actually read that function, which implements all of them via
> a generic reference-path walk rather than named per-kind derivation
> code). A3's structural validators are partially present
> (`workflow.rs::validate`, `schema.rs`'s ApprovalPolicy quorum check);
> not independently re-verified against this RFC's full A3 list
> (illegal terminal transitions, hook arity) in this pass. Part of the
> [RFC 0021 family](0021-typed-hi-graph-mcp-and-incremental-authoring.md).
> Only v2 `.nir` is supported by this RFC family. This document defines
> authoring data and validation, not a source-language execution path —
> see [RFC 0021.b](0021.b-approval-runtime.md) for the runtime.

## Motivation

A process needs explicit states, events, conditions and action bindings
before an agent can reason about it or a runtime can implement it.
Capture that design incrementally through the core graph/MCP service.

## Non-goals

No workflow execution, approval decisions, identity-provider integration,
transactions against application data, outbox dispatch or live-instance
migration. Those belong to [RFC 0021.b](0021.b-approval-runtime.md). Semantic proofs and
whole-program reachability belong to [RFC 0021.c](0021.c-graph-analysis.md). Storing or
accepting a definition does not assert that its behavior is enforced.

## Design

### Registered schemas and graph representation

Register `Workflow`, `WorkflowState`, `WorkflowTransition` and
`ApprovalPolicy` with independent versioned TypedSpec schemas, using
the core's immutable per-spec schema discriminator. States/transitions
are real addressable graph nodes, not unversioned nested objects.
All references use stable IDs; registry validators check their kinds.
The Workflow spec's state/transition member lists are authoritative;
the service derives containment edges and verifies each child's parent.
Related membership changes must occur in one patch to avoid inconsistent
parent/child ownership. Partial definitions use the core gap lifecycle.

The authoring schemas record conditions and actions as data:

- Conditions use the core Expression representation and bindings to
  workflow data, event, actor context and decision-summary references.
- Action bindings reference Function IDs and typed argument/result
  bindings; order is explicit, and a referenced function may still have
  an intentionally unimplemented body slot.
- ApprovalPolicy records `identity_basis: distinct_person | distinct_subject`,
  maker-count convention, reviewer exclusions, stages/slots/quorums,
  role/claim IDs, cross-stage distinctness, decision lifetime, payload
  scope, rework and rejection behavior. Runtime interpretation is
  specified in [0021.b](0021.b-approval-runtime.md).
- References to Role/Claim declarations are validated; owners/eligible
  handlers are distinct from the approval requirements on a transition.

Derived edges: `CONTAINS` (workflow→state/transition), `TRANSITIONS_TO`
(state→state with transition ID), `ON_ENTRY`/`ON_EXIT` (state→function
with ordered binding ID), and `REQUIRES_APPROVAL` (state/transition→policy).
Clients edit source specs; derived edges are recomputed atomically for
both proposal and exact accepted views according to core rules.

The current v2 [`workflow!`](../crates/nirdosha-macros/src/workflow.rs)
provides a state/transition shape and pure transition function. Its
hook identifiers do not implement the bound actions specified here.
Import must preserve that limited observation without asserting runtime
guards, quorums or action execution that the source does not establish.

### State and transition model

The minimum logical structure, with every referenced object having a
stable ID and schema-validated specification, is:

```text
Workflow
  data_type, definition_version
  initial_state_id
  state_ids[], transition_ids[]
  invariants[]

WorkflowState
  workflow_id, name
  entry_conditions[]          predicates over prospective entry context
  invariant[]                 predicates required while state is active
  exit_conditions[]           predicates over source context
  on_entry[]                  ordered, bound function calls
  on_exit[]                   ordered, bound function calls
  owner_policy_id             eligible handlers, not automatic approval
  approval_policy_id?         decisions collected while in this state
  terminal                    none | success | rejection | cancellation

WorkflowTransition
  workflow_id, from_state_id, to_state_id
  event_type, event_bindings
  actor_policy_id
  guard[]                     transition-specific predicates
  approval_policy_id?         quorum required for THIS transition
  update_plan_id?             typed transactional data updates
  on_failure, timeout_policy?
```

Conditions are pure checks; hooks are actions. Each hook references a
real function node with typed bindings for workflow data, instance ID,
event, verified actor and supported resources. Validate its signature
and effects. A hook name or prose description alone is a gap, not an
executable action. A self-transition explicitly declares whether it
re-enters the state and reruns hooks; there is no implicit interpretation.

State exit conditions apply to every outgoing transition. Put
approval-only gates on the approval transition, so rejecting/cancelling
a request is not accidentally blocked until it obtains approval.
Cancellation exceptions, if needed, are explicitly modeled transitions
with explicit semantics, not a hidden bypass of state conditions.
Terminal states have no ordinary outgoing transitions; reopening is a
separate modeled policy/transition or a new instance.

### Structural validation and capability declarations

This RFC validates declared structure: unique scoped state/event names,
one initial state in the owned set, legal source/target references,
terminal/reopen declarations, hook arity and supported binding types,
declared role/claim references, positive quorum values and satisfiable
literal slot counts (a two-slot group cannot demand three slots).
It checks neither the actual identity population nor arbitrary predicate
satisfiability, deadlocks or eventual completion. Such cases remain
gaps or are handed to 0021.c with explicit analysis coverage.

Store `required_runtime_capabilities` on the workflow, including
`guarded_transitions`, `durable_approval_ledger`, `distinct_person`,
`transactional_hooks`, and `outbox` as applicable. Host-installed runtime
adapters publish a versioned capability manifest and identity-authority
requirements. Agents may request these capabilities but cannot attest
that an implementation provides them. Capability declaration and actual
checker/build evidence remain separate records.

Graph acceptance can select a structurally complete definition for
review/export while its execution readiness is unsupported. Return
separate `authoring_ready` and `runtime_capability_ready` statuses.
Core `specification_ready`/`emission_ready` use the requested emission
scope: if the application would execute this workflow, missing runtime
support blocks emission. In particular, a distinct-subject runtime cannot
satisfy `distinct_person` by silently changing the policy. This RFC emits
only graph JSON/spec exports; executable lowering needs 0021.b support
and an explicitly registered v2 adapter.

## Effect on the permission model

Core proposal/acceptance grants authorize design edits. They do not
grant application roles or record live approvals. Identity declarations
and authority references are design inputs; real person mappings remain
operator-owned runtime data. Plugin-protected policies retain core
protections. Changing a proposed policy leaves accepted history intact.

## Compatibility

An optional schema registry extension; no required storage-format change
beyond core registered TypedSpec support and no new `.nir` dialect.
Existing v2 source is imported only to the extent the observer supports.
No interpretation of a wizard, arbitrary call graph or hook label as an
enforced workflow. Old accepted schema revisions stay readable through
the core versioning contract.

## Acceptance criteria

| Stage | Deliverable | Evidence |
|---|---|---|
| A1 | Registered non-executable specs and derived edges | Create/read/export states, transitions and policy by ID through MCP; matching versioned schemas |
| A2 | Incremental authoring and acceptance | Partial definition persists as gaps; atomic parent/member edits; exact dependency pins; accepted edges remain independent of proposals |
| A3 | Structural validators | Reject undefined roles/states/hooks, bad bindings, illegal terminal transitions and impossible literal slot counts; support explicit self-transitions and rework |
| A4 | Capability-aware UI/export | Unsupported runtime visible; distinct-person emission request blocked when only subject support exists; no execution side effects |

End-to-end fixture: stream a draft/review/completed workflow, add entry/
exit predicates and two approval slots, retrieve each state and hook edge
from another MCP client, resolve authoring gaps and accept exact revisions.
Export the definition, then request executable lowering without a runtime
adapter and assert `UNSUPPORTED_TARGET`. No ledger or identity provider
is needed to pass this document's acceptance criteria.

## Open questions

Future schemas may add hierarchical/parallel state regions. The initial
schema covers one active state per instance; parallel reviewer collection
within a state does not imply parallel state-machine regions.

## Rejected alternatives

- Treat hook labels as executed functions: loses bindings and falsely
  claims behavior not supplied by the current v2 macro.
- Embed runtime approvals in authoring nodes: conflates design changes
  with authenticated decisions on application instances.
- Require runtime implementation before storing a workflow: prevents
  useful design capture and inspection of unresolved capabilities.
